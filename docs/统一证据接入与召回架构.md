# 统一证据接入与召回架构

本文说明 `/analysis` 后续证据层的目标形态：MySQL、上传文档、图片、网站等外部信息源，不直接进入 Agent 回答，而是先沉淀为 `来源` 面板里的统一条目，再归一成 `EvidenceNode`，交给 `EvidenceRetrievalService` 统一召回、重排、融合，最终生成带来源的自然回答。

这份文档面向评审和后续工程落地。它描述目标架构，也标出当前仓库已经具备的基础能力，避免把未收敛完成的统一证据层误说成现状。

这里的 `来源` 不是单纯的 UI 入口。它是所有证据材料完成后的统一产品对象。MySQL 查询、文档解析、图片 OCR / 视觉理解、网页抓取、资料包构建和当前分析结果，完成后都必须回到 `来源` 面板，成为可选择、可管理、可引用的来源条目。其他区域只消费已选来源，不保存独立资料结果。

## 1. 背景与目标

当前 `/analysis` 已经有多种证据来源：

- 当前地图分析结果：POI、H3、路网、人口、夜光、等时圈等。
- 上传材料：PDF、Office、图片、文本等，完成后分别成为 `document source` 或 `image source`。
- 文档索引：文档解析、PageIndex 结构和页内容检索。
- 网页资料：Crawl4AI 抓取后的 Markdown、摘要和段落节点。

这些来源的数据形状差异很大。MySQL 查询返回结构化行，PageIndex 返回章节与页码，图片处理会返回 OCR 文本和视觉描述，网页抓取返回 Markdown chunk。若 Agent 直接理解每种来源，会把数据源细节泄漏到工具循环、Finalizer 和前端展示里。

统一证据层要解决三件事：

1. 让所有来源先转换成同一种证据节点。
2. 让 Agent 只面对“可引用证据”，而不是面对每种数据源的内部格式。
3. 让最终回答能说明来源、定位和可信边界。

产品层还需要守住一条规则：所有资料接入、解析、构建和状态管理都以 `来源` 为归宿。用户选择的是来源；Agent、PPT 指令文件和后续页面生成使用的是已选来源背后的证据节点。

目标链路可以概括为：

```text
用户问题
-> 来源区发起 / 接收资料
-> 后端解析或构建
-> 生成 Source 条目
-> 数据源适配器解析 / 清洗 / 归一化
-> EvidenceNode
-> EvidenceRetrievalService 召回、重排、融合
-> Finalizer 基于证据包生成带来源回答 / 生成内容
-> 会话持久化，保留引用与诊断
```

## 2. 来源是统一归宿

`来源` 面板承担两层职责：

1. 入口职责
   用户从来源区添加、上传、搜索、接入或生成资料。上传文档、上传图片、AI 搜索网页资料、生成资料包、读取当前分析结果，都从这里发起或回到这里显示。

2. 归宿职责
   每个完成结果都变成一个 `Source` 条目。来源树展示已完成、构建中、失败和待重试的资料。右侧工作区、聊天区和生成流程只引用这些来源，不再持有独立资料对象。

一个 `Source` 条目至少需要表达：

| 字段 | 含义 |
| --- | --- |
| `source_id` | 来源唯一 ID，如 `document:...`、`web:...`、`database:...`、`image:...`、`package:...`。 |
| `title` | 用户在来源树中看到的标题。 |
| `source_kind` | 来源类型，如 `system`、`document`、`image`、`web`、`database`、`package`。 |
| `status` | `ready`、`generating`、`failed`、`pending` 等状态。 |
| `summary` | 来源摘要，用于来源列表和 AI 输入预览。 |
| `evidence_count` | 可用于召回和引用的证据节点数量。 |
| `locator_summary` | 页码、URL、SQL 记录、图片区域或分析结果名称等定位信息。 |
| `availability` | 是否可被 Agent / PPT 生成消费，以及不可用原因。 |

这条规则会让产品心智更稳：用户只管理来源，系统只消费来源。内部可以保留解析文件、PageIndex、chunk、SQL rows、OCR 片段和临时 payload，但这些中间产物不能成为用户可见或 Agent 可消费的独立产品对象。

## 3. 四类外部证据入口

### 3.1 当前范围数据源：受控查询接入

当前范围数据源是 `/analysis` 主 AI 需要的结构化证据入口。它的产品语义不是“MySQL”，而是当前 `history_id`、当前空间范围、当前年份或数据版本下的 POI、人口、夜光、路网和 H3/栅格数据。实现上可以读取 `poi_results`、`analysis_artifacts` 或运行时 artifacts，但 Agent 不直接面对数据库表结构。

接入方式：

- 通过 scoped dataset 工具列出当前范围可用数据源。
- 对数据源执行受控过滤、排序、聚合、分页和单条读取。
- 查询结果统一转换为结构化 `EvidenceNode`。
- 每个节点保留 `source_id`、记录 ID、年份或数据版本、定位信息和查询口径。

当前仓库已有基础：

- POI 完整列表保存于 `poi_results.poi_data`，按 `history_id + source + year` 区分。
- 路网、H3/POI 栅格、人口和夜光等范围产物保存于 `analysis_artifacts.payload`。
- 人口和夜光重新跑分析后会保存完整 `payload.grid.features`，同时保留当前视图的 `layer.cells`、抽样 evidence 和预览信息，可作为后续 scoped dataset 查询底座。
- `analysis_artifacts.payload` 内部已收敛为统一载体：网格类使用 `payload.grid`，图层指标使用 `payload.layer`，路网使用 `payload.roads` / `payload.nodes`，年份和视图同时写入 `params` 与 `payload`。
- `modules/scope_datasets/` 已提供第一版受控读取层，并通过 Agent 工具注册 `list_scope_datasets`、`query_scope_dataset`、`aggregate_scope_dataset` 和 `read_scope_record`。

后续收敛方向：

- 在来源树中展示当前范围数据源的标题、年份、记录数、可用字段和警告。
- 继续扩展 scoped dataset 字段白名单、中文字段别名和聚合能力。
- 让 scoped dataset 查询结果进一步进入统一 EvidenceNode 召回、去重和引用排序。

### 3.2 上传文档：解析、PageIndex 与向量检索接入

上传文档负责承接 PDF、Word、PPT、表格和文本资料。用户从来源区上传文档；文档解析、PageIndex 和向量索引完成后生成 `document source`。系统不直接把全文塞给模型，而是拆成可检索、可定位、可引用的证据节点。

接入方式：

- 先完成文件解析，提取正文、标题、表格和页码。
- 使用 PageIndex 建立文档结构，保留章节、页码和块位置。
- 使用向量检索或轻量关键词检索召回相关片段。
- 将命中文本、章节摘要、页码范围写入 `document source` 背后的 `EvidenceNode`。

每个文档证据节点至少保留：

- 文档 ID、文件名、文档角色。
- 页码范围、章节标题、块索引或 PageIndex line。
- 原文片段、摘要、解析警告。
- 可展示 citation，例如 `文件名，第 5 页` 或 `PageIndex line 5`。

当前仓库已有基础：

- `modules/documents/` 已包含文档上传、解析、block、PageIndex 相关能力。
- `modules/evidence_retrieval/service.py` 已能基于 PageIndex 做文档证据搜索。
- `modules/retrieval/attachments.py` 保留内部文件解析、chunk 写入和读取能力。

后续收敛方向：

- 文档搜索结果统一输出 `EvidenceNode`，旧的表格行结果只作为由节点派生的 view model 保留。
- 来源面板只展示 `document source`，不再把“附件”“PageIndex 结果”“检索结果”拆成多个产品对象。
- PageIndex、内部文件 chunk、向量命中结果进入同一重排通道。

### 3.3 图片：OCR、图像描述和视觉理解接入

图片证据包括用户上传的截图、图纸、照片、扫描件和报告中的图片页。用户从来源区上传图片或包含图片的文档；OCR、图像描述和视觉理解完成后生成 `image source` 或并入对应 `document source`。图片不能只作为文件存在，必须经过可解释的视觉解析后才能进入回答。

接入方式：

- OCR 提取图片中的文字。
- 图像描述生成场景、对象、图表、地图符号等视觉摘要。
- 视觉理解模型识别图中关键关系，例如图例、标注、表格结构、地图范围或异常区域。
- 将 OCR 文本、视觉描述和结构化识别结果写入来源背后的 `EvidenceNode`。

每个图片证据节点至少保留：

- 图片文件 ID、文件名、所属来源。
- 识别类型：`ocr_text`、`image_caption`、`visual_analysis`。
- 图片区域、页码或坐标定位。
- 识别置信度、模型来源、解析警告。
- 引用文本，例如 `现场照片，第 3 页图片，OCR 片段`。

当前仓库已有基础：

- 内部文件解析链路已允许图片类文件上传。
- 图片附件 ingest 已迁到 `ImageVisualIndex` contract，当前写入图片索引节点和 `image_visual_index.json`；目标处理器是 PaddleOCR/PP-Structure、OpenCLIP 和 Qdrant。

后续收敛方向：

- 把图片 OCR、图像描述、视觉分析结果拆成可独立引用的 `EvidenceNode`。
- 在来源树中让图片作为独立 `image source` 或文档来源下的证据能力出现，避免出现独立“图片结果”面板。
- 回答中必须区分“图片原文 OCR”和“模型视觉判断”，避免把视觉推断说成原始资料。

### 3.4 网站：Crawl4AI、Markdown 清洗和网页 chunk 接入

网站资料用于补充外部背景、政策材料、新闻信息或公开网页说明。用户从来源区发起 AI 搜索或输入 URL；Crawl4AI 抓取、Markdown 清洗和 chunk 构建完成后生成 `web source`。网页抓取结果需要先清洗噪声，再转换成可引用节点。

接入方式：

- 使用 Crawl4AI 抓取网页。
- 将网页内容转成 Markdown。
- 清洗导航、无障碍控件、脚本链接等噪声文本。
- 按标题、段落或语义块切成网页 chunk。
- 将 chunk 写入 `web source` 背后的 `EvidenceNode`。

每个网页证据节点至少保留：

- URL、网页标题、抓取时间。
- chunk 标题、序号和摘要。
- 原文片段、清洗警告、抓取状态。
- citation，例如 `网页标题，URL，段落 3`。

当前仓库已有基础：

- `modules/web_crawler/crawler.py` 已接入 Crawl4AI。
- 该模块已包含 Markdown 清洗、标题提取、摘要生成和网页节点构建逻辑。

后续收敛方向：

- 网页节点不直接作为独立 crawler payload 进入 Agent。
- 来源面板只展示 `web source`，不把搜索结果、抓取结果和网页 chunk 拆成三类产品对象。
- 抓取后的网页 chunk 统一进入 `EvidenceRetrievalService`，与文档、数据库、图片证据一起排序。

## 4. EvidenceNode 统一模型

`EvidenceNode` 是 Agent 可以引用的最小证据单元。它不等同于原始数据，也不等同于最终结论。它只表达一条可定位、可复核、可参与排序的证据。

建议概念字段如下：

| 字段 | 含义 |
| --- | --- |
| `id` | 证据节点唯一 ID，包含来源类型和稳定定位信息。 |
| `source_id` | 所属来源 ID，指向来源树中的统一产品对象。 |
| `source_type` | 来源类型，如 `system`、`document`、`image`、`web`、`database`、`package`。 |
| `title` | 给 Agent 和前端展示用的短标题。 |
| `content` | 可供回答引用的正文、结构化摘要或视觉描述。 |
| `summary` | 短摘要，用于列表展示和上下文压缩。 |
| `metadata` | 来源内部元数据，如表名、字段、页码、URL、图片区域、抓取时间。 |
| `locator` | 可复核定位，如 `page:5`、`row:123`、`url#section-3`、`image:box(...)`。 |
| `score` | 检索或重排后的相关性分数。 |
| `evidence_level` | 证据等级，如 `raw_record`、`parsed_text`、`ocr_text`、`visual_inference`、`derived_metric`。 |
| `warnings` | 解析失败、低置信度、字段缺失、网页噪声等警告。 |
| `citation` | 最终回答可展示的引用文本。 |

设计原则：

- 每个 `EvidenceNode` 必须挂在某个 `Source` 下面。
- 来源细节放进 `metadata`，不要让 Agent 为每种来源写分支逻辑。
- `content` 必须能独立支撑引用，不能只放 ID 或空泛摘要。
- `citation` 必须面向用户可读，不能只展示内部主键。
- `warnings` 是答案边界的一部分，Finalizer 需要看到它。

## 5. EvidenceRetrievalService 职责

`EvidenceRetrievalService` 是统一证据层的核心。它不负责解析每种数据源的全部细节，而负责接收各适配器产出的 `EvidenceNode`，再按用户问题组织证据包。

它的职责包括：

1. 收集证据源
   根据来源树中的已选 `Source`，确认本轮可用证据源。当前会话、文档来源、图片来源、数据库来源、网页资料和分析快照都必须先回到来源对象。

2. 召回候选证据
   对文本 chunk、结构化数据库摘要、OCR 文本、图片描述、网页段落和当前分析结果做统一召回。

3. 重排证据
   综合关键词命中、向量相似度、来源优先级、证据等级、时间、用户显式选择和解析质量进行排序。

4. 融合证据
   合并重复节点，保留互补节点。若两个节点来自同一文档页或同一数据库记录，服务层应减少重复引用。

5. 输出引用包
   给 Finalizer 输出一个紧凑证据包，包含关键节点、引用文本、警告和来源列表。

6. 保留诊断
   当没有命中、来源解析失败或证据质量不足时，返回明确诊断，帮助 Agent 说明缺口。

建议输出给 Finalizer 的结构保持紧凑：

```text
question
top_evidence_nodes
source_summary
warnings
missing_evidence
citation_map
```

Finalizer 只基于该证据包生成回答，不再直接理解 MySQL 行、PageIndex 原始结构、图片处理 payload 或 Crawl4AI 原始结果。

## 6. Agent 回答如何带来源

统一证据层进入 Agent 后，回答链路应保持三条规则。

第一，结论必须绑定证据节点。
Agent 可以归纳和解释，但关键判断必须能追溯到 `EvidenceNode.id` 和 `citation`。

第二，引用要面向用户。
用户看到的来源应是文件名、页码、网页标题、数据库记录摘要或分析结果名称，而不是内部对象路径。

第三，边界要随证据一起进入回答。
如果图片 OCR 低置信度、网页清洗质量差、数据库字段缺失、文档只命中少量片段，Finalizer 应在回答中保留限制条件。

最终回答可以采用这种内部组织：

```text
直接回答用户问题
-> 说明最关键证据
-> 给出来源引用
-> 必要时说明证据缺口或不确定性
```

前端只负责展示回答、引用和过程信息，不复制后端的检索、重排和证据融合逻辑。

后续增强集中在证据质量和检索效果，而不是新增产品入口：

1. `KnowledgeChunk`、`AttachmentChunk` 继续只作为内部解析 / 检索中间模型存在，对外契约只暴露 `Source` 和 `EvidenceNode`。
2. 在 `EvidenceRetrievalService` 中继续增强多来源统一重排、融合和 citation map。
3. 补齐 package / database source 的可解释重建、重试前后的诊断对比，以及空证据原因展示。

当前产品对象和 Agent / PPT 消费契约已经收敛到来源和证据节点。各来源的解析细节留在所属模块内部。

### 7.1 当前收敛状态

当前代码已进入“单一证据契约收敛”阶段：

- `modules/evidence_retrieval/schemas.py` 已有 `SourceRecord` 和 `EvidenceNode`。
- canonical `SourceKind` 已收敛为 `system`、`document`、`image`、`web`、`database`、`package` 六类。

- `modules/evidence_retrieval/adapters.py` 开始承接来源适配器职责，读取 canonical `evidence_nodes`，并把当前分析 `KnowledgeChunk`、内部文件 `AttachmentChunk` 转成 `EvidenceNode`。
- PPT 来源模型已显式携带 `source_kind`、`summary`、`evidence_count`、`locator_summary`、`availability`，减少核心状态对 `meta` 的依赖。
- 网页来源 ID 已统一为 `web:*`；网页来源后端模块和 HTTP 路由已收敛为 `modules/ppt_web_source/`、`router/domains/ppt_web_source.py` 和 `/api/v1/analysis/ppt/web-sources/*`。
- 网页来源产品元数据已统一写入 `meta.web_source`；来源证据计数只依据 canonical `evidence_nodes` 和显式 counts。
- Agent retrieval tools 搜索和读取当前分析 / 报告上下文时，主返回已切到 `evidence_node`；读取工具已收敛为 `read_analysis_evidence_node` / `read_report_evidence_node`，对外只接收 `node_id`。搜索命中和读取结果中的 EvidenceNode 使用 `:node:` 语义 ID，metadata 不再暴露底层解析键。普通聊天文件不再作为独立资料入口。
- 旧数据库 Agent tools 已从主工具目录移除；面向用户的结构化数据查询后续收敛到 scoped dataset 工具。
- scoped dataset Agent tools 已进入主工具目录，当前范围 POI、H3、人口、夜光和路网明细通过 `list_scope_datasets`、`query_scope_dataset`、`aggregate_scope_dataset` 和 `read_scope_record` 查询，不再通过旧数据库记录工具替代。
- `finalizer_evidence_pack` 已只输出 `evidence_nodes` 作为最终回答前的证据字段。
- 文档来源、图片来源、网页来源、数据库来源和资料包来源的后端生产路径已直接在 `aiPayload` 中输出 `evidence_nodes` / `evidenceNodes`。
- `EvidenceRetrievalService` 从来源 payload 回读证据时，只读取 canonical `evidence_nodes`。
- 统一证据搜索响应已只输出 canonical `nodes`。
- `EvidenceSearchRequest` 已去掉独立 `document_ids` 请求契约，文档 PageIndex 检索由 `source_ids` 中的 `document:*` 来源 ID 派生，避免文档绕过来源对象。
- 文档来源列表已将 PageIndex preview 转成 `document EvidenceNode`，后端输出 `evidence_nodes`；前端优先使用后端标准 payload。
- 当前分析 `system source` 的轻量证据已在前端按 EvidenceNode 形状派生，并只写入 `evidence_nodes`。
- PPT quick ask 和 Context Ask 的所选来源摘要已优先携带、压缩 `evidence_nodes`，发送给 Agent 的目标上下文不再暴露裸 evidence view。
- PPT LLM context bundle 已将所选来源 evidence 转成紧凑 `EvidenceNode`，通过 `evidence_context` / `evidence_node_context` 提供给目录、叙事和逐页指令生成。
- PPT 来源模型、transport 摘要、来源健康状态和 delivery manifest 已识别 `evidence_nodes` / `EvidenceNode` 作为证据计数和可用性判断依据。
- 前端新构建的 PPT `aiPayload` 已同步携带 `evidence_nodes` / `evidenceNodes`。

- 普通 Agent 聊天区的独立文件入口、文件状态会话契约和上传文件检索工具已移除；文件解析链路仅作为文档 / 图片来源构建的内部管线保留。
- 图片来源上传、删除和重试的 HTTP 边界已收敛到 `/api/v1/analysis/ppt/image-sources`，不再暴露为 Agent attachments API。
- 网页来源除地区资料搜索包外，后端 preview 已支持直接传入 URL，抓取后生成 `web:{area_id}:{hash}` 来源，并由网页 chunk 派生 `web EvidenceNode`。
- 网页来源 preview / commit / 默认位置的 HTTP 边界已收敛到 `/api/v1/analysis/ppt/web-sources/*`；`/ppt/research/*` 不再作为新增网页来源的产品 API。
- 网页来源持久化 artifact type 已收敛为 `ppt_web_source`。
- PPT 来源区已提供“联网来源”统一入口，用户可以从来源面板发起 AI 搜索，也可以直接添加 URL；前端会把 URL 透传到同一 preview / commit 链路，完成后仍作为来源树中的 `web source` 出现。

- 系统、文档、网页、数据库、资料包来源的后端生产路径已开始统一填充 `evidence_count`、`locator_summary`、`availability`，来源树不再只依赖前端猜测可用性和定位信息。
- PPT 来源区的“添加来源”已支持图片文件；图片通过内部文件解析链路构建 OCR / 图像描述 / 视觉理解证据，完成后以 `image:{attachment_id}` 的 `image source` 出现在来源树中，并可被选择、删除和作为 PPT / Agent 输入消费。
- 来源树已具备基础重试动作：失败或空证据的 `document source` 可重新触发 PageIndex 解析，`image source` 可重新触发图片解析，`web source` 可重新 preview / commit，完成后仍回到来源树。

后续增强：

- `KnowledgeChunk` 和 `AttachmentChunk` 仍作为底层检索 / 文件解析内部中间模型存在；对 Agent 工具、HTTP 契约和产品文档不再作为产品对象暴露。转换为 EvidenceNode 后，外部只看到 `node_id`、`source_id`、引用定位和证据内容。
- 来源重试仍是基础动作，后续需要继续补齐 package / database source 的可解释重建、重试前后的诊断对比，以及空证据原因展示。

## 8. 边界与不做什么

统一证据层需要保留清楚边界。

- 不在来源之外保留独立资料结果。用户可见和 Agent / PPT 可消费的资料对象只叫来源。
- 不让右侧工作区、聊天区或生成流程直接持有外部材料。它们只能消费已选来源。
- 不让同一份材料同时以“附件、网页结果、检索结果、临时 payload”等多个产品对象出现。
- 不做任意 SQL。结构化数据必须通过 scoped dataset 或来源适配器的受控查询进入证据层。
- 不把 OCR 当绝对事实。OCR 文本必须带来源、区域和置信度或警告。
- 不把视觉理解当原始证据。视觉判断属于 `visual_inference`，回答时要区分推断和原文。
- 不把网页噪声当可靠资料。Crawl4AI 结果必须经过 Markdown 清洗和 chunk 质量检查。
- 不让前端复制证据融合逻辑。前端展示来源，后端决定召回、排序、融合和引用。
- 不为旧 payload 保留双字段兼容。目标态应收敛到单一 `EvidenceNode` 契约。
- 后端可以保留内部中间产物，但最终必须把可见结果收敛回 `Source`。

## 9. 简短结论

统一 EvidenceNode 架构的价值不在于增加一个新名词，而在于让所有外部资料都先变成来源，再变成可复核证据，最后参与 Agent 回答和 PPT 生成。

对评审来说，这条链路能说明系统为什么可信：答案不是模型直接编出来的，而是来自可定位的当前范围数据、文档页、图片解析片段、网页段落和当前分析结果。

对工程来说，这条链路能减少跨层耦合：来源适配器负责生成 `Source` 和 `EvidenceNode`，`EvidenceRetrievalService` 负责召回与融合，Agent 和 PPT 生成只负责基于已选来源回答或生成内容。
