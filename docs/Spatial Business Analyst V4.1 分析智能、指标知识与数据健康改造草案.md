# Spatial Business Analyst V4.1：分析智能、指标知识与数据健康改造草案

> **状态：待产品微调。** 这是一份设计草案，不代表已完成实现。
>
> **核心目标：** 让主 Agent 像一个真正的前期商业空间分析师一样，理解项目、提出假设、选择并组合指标、比较项目内部差异、解释这些差异可能意味着什么，并转化为选址、布局、店型、选品、服务和验证建议。

V4.1 不以增加审计字段为目标。数据健康、口径一致和代理指标边界应尽量由底层模块自动处理，不能让报告和 Agent 工作流变成证据台账。

---

## 1. 设计原则：分析智能优先，治理规则下沉

V4.1 应优先提升五种分析能力：

1. **理解项目：** 判断是 B2C、B2B 还是 mixed，谁付款、谁使用、怎样履约、当前真正要决定什么；
2. **提出假设：** 在执行工具前，形成可能影响选址、布局、店型、选品或服务方案的项目假设；
3. **选择和组合指标：** 不按人口、POI、夜光、路网机械拆章，而是围绕同一个决策问题组织多项证据；
4. **进行项目内比较：** 用户给候选点时比较候选点，用户只给区域时比较区域内部网格或分区；
5. **解释并形成行动：** 从“哪里不同”继续推到“可能是什么空间机制”“会改变什么项目动作”“下一步如何验证”。

治理只保留三条底线，并尽量在底层自动完成：

- 同一次比较必须使用一致的数据版本、空间单元和算法参数；
- 数据不可用或覆盖不足时，结果要明确降级，不补造数值；
- 人口、夜光、POI、路网等空间信号不能被单独写成已经发生的消费、客流、营收或 ROI。

除这三条外，不在主流程中增加大量审批状态、结论级别、禁词清单和审计绑定字段。

---

## 2. 目标工作流

```text
理解项目与决策
  → 识别候选对象或生成内部比较单元
  → 提出决策假设
  → catalog() 快速发现可用指标
  → detail(tool_id) 学习指标含义、比较方法和组合方式
  → 形成简洁的 analysis approach
  → 底层自动检查数据健康并执行同口径比较
  → 主 Agent 综合多项指标，解释空间机制
  → 形成选址、布局、店型、选品、服务与验证建议
  → 主分析师做专业审校并编译报告
```

公开运行工件仍只包括：

```text
source-index.json
analysis-plan.json
chapters/<chapter-id>.v1.json
chapters/<chapter-id>.v2.json
editorial-review.json
report/project-report.md
report/assets/*.svg
```

不新增独立基准库、审计台账或指标审批文件。

## 3. 双层指标目录：从“治理目录”改成“分析知识库”

### 3.1 `catalog()`：告诉 Agent 有什么

`catalog()` 保持现有 7 个轻量字段：

- `tool_id`
- `name`
- `purpose`
- `question_tags`
- `primary_spatial_unit`
- `action_targets`
- `implementation_status`

它只负责快速发现。主 Agent 浏览后应该能判断：

- 这个工具是否与当前决策问题有关；
- 它主要分析候选点、范围、网格、路径还是等时圈；
- 它可能影响选址、布局、服务范围、店型、选品场景或履约中的哪一类行动；
- 当前是否真的可以执行。

名称和用途必须写成真实测量对象。例如：

- 使用“夜间亮度空间分布”，不使用“夜间经济强度”；
- 使用“服务范围内人口分布”，不使用“消费人口覆盖”；
- 使用“空间条件候选网格”，不使用未经验证的“商业机会网格”。

### 3.2 `detail(tool_id)`：告诉 Agent 怎么用

`detail()` 不应成为一份很长的治理清单，而应成为 Agent 能直接吸收的“指标分析卡”。每个工具重点回答五个问题。

#### 1. `measures`：它测量什么

包括：

- 简明定义；
- 单位和主要输出；
- 支持的空间单元；
- 时间语义；
- 必要时给出计算方法。

目标是防止 Agent 因工具名称产生错误理解。

#### 2. `use_for`：它适合回答什么项目问题

包括：

- 适用的决策问题；
- 可能影响的行动；
- 在 B2C、B2B 或 mixed 项目中的典型用途。

例如 POI 类指标不能只写“支持设施分析”，而应写成：

> 比较候选点周边设施结构，识别不同点位更接近社区生活、办公通勤、文旅停留、产业服务或物流履约中的哪类空间场景，从而调整踏勘重点、店型或服务方案假设。

#### 3. `compare_by`：它通常应该怎么比

为 Agent 提供可直接使用的比较方法，而不是让 Agent临时搜索或自行发明口径。例如：

- 候选点之间使用相同出行方式和时间阈值的等时圈；
- 项目内部使用同分辨率、同覆盖规则的网格；
- 数量指标在面积不一致时优先比较密度或构成比；
- 类别指标同时比较数量、占比和组合，不只比较总量；
- 路网指标在相同网络模型和半径参数下比较；
- 小样本优先写具体差值和组内排序，不写伪精确分位数。

`compare_by` 只提供通用分析方法。本次项目具体比较 A/B/C，还是比较内部网格，由主 Agent 根据项目输入决定。

#### 4. `interpret_with`：结果应该和什么一起解释

这是提升分析智能最重要的部分。它告诉 Agent：单个指标如何与其他指标、项目材料和业务问题组合。

例如：

```text
POI 结构
  + 人口分布
  + 路网与等时圈
  → 判断某候选点更接近哪类服务场景

夜间亮度
  + 夜间营业 POI
  + 公交/道路接入
  → 判断是否值得提出夜间服务时段假设

企业 POI / 园区分布
  + 驾车等时圈
  + 路网与物流设施
  → 判断 B2B 服务节点和客户拜访优先级
```

每个指标详情应给出：

- 常见的互补指标；
- 可以形成的组合判断；
- 出现矛盾结果时应怎样继续分析；
- 哪些项目材料或现场信息可以帮助解释。

#### 5. `watch_out`：最少但关键的解释提醒

只保留会显著误导分析的少量提醒，例如：

- POI 是设施记录，不等于真实营业、需求或客流；
- 人口是服务对象分布，不等于购买力；
- 夜光是亮度信号，不等于夜间消费；
- 路网是结构可达性，不等于真实通行量；
- 等时圈是模型覆盖，不等于实际到访。

不为每个工具堆叠大段“禁止结论”和审批规则。公共边界由 Skill 的总规则统一说明，指标详情只补充该指标独有的误读风险。

### 3.3 现有目录如何收敛

当前 `metric-catalog.yaml` 已有 54 个工具，并已包含 `definition`、`supports`、`does_not_support`、`actionability`、`valid_comparisons`、`quality_requirements` 和 `followup_metrics` 等内容。

不需要推翻重写，可以按下面方式整理：

| 现有内容 | V4.1 分析知识卡 |
| --- | --- |
| `definition`、`unit`、`outputs`、`spatial_granularities` | `measures` |
| `answers_questions`、`supports`、`actionability` | `use_for` |
| `valid_comparisons`、现有 `comparison_baseline` 中的同口径要求 | `compare_by` |
| `followup_metrics` 加上业务解释模板 | `interpret_with` |
| `does_not_support` 中最关键的误读风险 | `watch_out` |
| `quality_requirements` | 底层 `data_health`，不全部暴露给作者 |

当前最大的缺口不是目录没有内容，而是 `MetricDetail` 没有把这些分析知识完整返回给 Agent。V4.1 应优先解决“详情真正可用”，而不是继续增加字段数量。

## 4. 分析计划：从逐指标审批改成章节分析思路

不再设计包含大量许可、禁止、基准请求和状态字段的 `metric_use_plan`。在 `analysis-plan.json` 中，每个章节增加一个简洁的 `analysis_approach`。

```json
{
  "chapter_id": "site-and-format",
  "decision_question": "A、B、C 中哪个点更适合进入首轮踏勘，不同点位分别适合验证什么店型？",
  "targets": ["site:a", "site:b", "site:c"],
  "hypotheses": [
    "A 可能更接近社区高频服务场景",
    "B 可能更接近办公和通勤场景",
    "C 可能更适合作为低成本试点或履约节点"
  ],
  "comparison_design": "对三个点生成相同参数的 10 分钟步行等时圈，并比较人口、设施结构、路网和夜间亮度分布。",
  "candidate_tool_ids": [
    "population.total",
    "poi.category_count",
    "road.integration",
    "nightlight.mean"
  ],
  "synthesis_goal": "解释各点更接近哪类服务场景，并形成差异化踏勘、店型和首批品类验证方案。"
}
```

这份结构的目的不是审批指标，而是让 Agent 在执行前先表达分析思路：

```text
我要回答什么
→ 当前有哪些可能解释
→ 比较哪些对象
→ 为什么选择这些指标
→ 最后要综合成什么决策
```

同一工具可以出现在不同章节，但必须服务于不同的决策问题和综合目标。作者仍可以在执行过程中发现某个指标无意义并放弃，也可以在有明确解释理由时补充一个相关工具，不需要经过复杂审批状态。

## 5. 项目内部比较：由分析引擎自动完成

项目内部比较不需要基准库，也不需要主 Agent 手工维护大量比较字段。主 Agent只需要确定“比较对象和比较方式”，底层分析模块负责把复杂度隐藏起来。

### 5.1 有候选点时

```text
A / B / C 候选点
  → 自动生成相同参数的等时圈或缓冲范围
  → 对每个候选点执行相同指标
  → 自动完成数据版本、参数和归一化对齐
  → 返回候选点比较表和空间图件
```

### 5.2 只有一个项目区域时

```text
项目区域
  → 根据尺度生成 H3 网格、规则网格或合理分区
  → 在相同空间单元上计算指标
  → 识别内部结构、连续片区、异常单元和方向差异
  → 生成候选区域与下一步踏勘位置
```

### 5.3 比较结果应面向分析，而不是面向审计

工具结果应直接给主 Agent 可用于推理的内容：

- 候选点或网格的指标对照表；
- 主要差异及差异幅度；
- 空间分布图；
- 可能需要结合其他指标解释的异常；
- 数据覆盖不足或不可比的简短提示。

例如：

```json
{
  "summary": "A 的生活服务类别占比高于 B、C；B 的办公和交通设施更集中；C 的设施总量较少但道路接入较直接。",
  "comparison_table": [
    {"target_id": "site:a", "dominant_structure": "community_service"},
    {"target_id": "site:b", "dominant_structure": "office_commute"},
    {"target_id": "site:c", "dominant_structure": "low_supply_direct_access"}
  ],
  "interpretation_prompts": [
    "结合人口分布判断 A 是否确实对应社区服务对象。",
    "结合工作日现场观察验证 B 的通勤场景。",
    "核查 C 是真实供给缺口还是 POI 更新和可进入性问题。"
  ]
}
```

结果不需要携带大量审计状态，只需保持数据来源可追溯，并在确实存在问题时说明限制。

## 6. 主 Agent 的分析智能

### 6.1 从单指标描述升级为多指标解释

报告不能按下面方式机械罗列：

```text
人口有多少
POI 有多少
道路有多少
夜光是多少
```

而应组织成：

```text
空间现象
  → 多项指标是否相互支持或矛盾
  → 可能对应什么使用场景或履约机制
  → 对本项目意味着什么
  → 应改变什么行动
  → 下一步验证什么
```

### 6.2 示例：B2C 选址、店型和选品

```text
A 点：社区生活 POI 占比较高
  + 服务范围内居住人口覆盖更连续
  + 步行路网较细密
  + 夜间亮度分布稳定

分析：A 更像全天候社区生活服务场景，而不是据此断言消费更强。

行动：
- 优先踏勘居民真实进入路径、可见性和临停条件；
- 优先验证高频补给、即时需求和家庭场景商品组合；
- 对早餐、晚间补给、家庭应急等时段和品类形成首轮访谈或试卖清单。
```

这里的“选品”来自对使用场景的推理，而不是由人口或 POI 直接计算 SKU 销量。

### 6.3 示例：B2B 节点和产品方案

```text
某候选节点：目标企业和园区分布较集中
  + 驾车服务范围能覆盖更多目标账户
  + 主干路和物流设施接入更直接
  + 同类服务设施较少

分析：该节点可能更适合作为企业拜访、交付或展示服务节点。

行动：
- 调整目标企业拜访顺序；
- 设计适合园区客户的产品或解决方案组合；
- 验证采购决策人、交付频率、响应时限和仓储需求；
- 再决定节点面积、人员和库存配置。
```

### 6.4 遇到冲突信号时继续分析

指标之间不一致不应被视为错误，而是分析价值。例如：

- 人口覆盖较高，但道路进入条件较差；
- POI 密集，但同类设施占比也高；
- 夜间亮度较高，但夜间营业设施很少；
- B2B 企业分布集中，但驾车服务范围被道路结构切割。

主 Agent 应解释冲突可能来自什么机制，并把冲突转化为候选方案差异、现场核查重点或试点条件，而不是强行合成一个总分。

## 7. 数据健康：保留，但隐藏在深模块内部

数据健康仍然必要，因为此前人口和夜光被 `record_count = 0` 错误判断为不可用。但健康检查不应成为报告主体，也不要求章节作者理解栅格、矢量和表格的内部检查细节。

统一由底层数据健康服务处理：

### 栅格

检查可读取性、年份、分辨率、NoData、分析范围相交、有效像元和覆盖比例。`record_count` 对栅格不适用。

### 表格 / 记录

检查年份、记录数、关键字段、去重、分类覆盖和与项目对象的关联能力。

### 矢量

检查有效几何、坐标系、范围相交、网格对齐、路网连通性和必要属性。

底层只向主 Agent 返回三种简单状态：

- `ready`：正常使用；
- `limited`：可以使用，但附带一句影响解释的限制；
- `unavailable`：不执行，并说明缺少什么。

报告只在限制确实影响结论时提及，不输出长篇健康审计清单。

---

## 8. 专业审校：检查分析质量，而不是字段合规

主分析师的审校重点应是：

1. 是否真正回答了项目负责人下一步要决定的问题；
2. 指标组合是否足以解释结论，是否遗漏关键反证；
3. 是否把空间差异转化成了选址、布局、店型、选品、服务或履约行动；
4. 是否解释了指标之间相互支持或冲突的机制；
5. 是否清楚区分“空间场景假设”和“已经验证的经营事实”；
6. 验证动作是否具体到对象、内容和改变决策的条件；
7. 是否存在机械罗列指标、泛泛免责声明或没有行动价值的段落。

只有明显把代理指标写成真实经营结果时才要求退修，不建立复杂的禁词扫描、逐条结论审计或行动等级审批体系。

---

## 9. 最终报告应该呈现什么

最终报告重点输出：

- 当前项目的商业模式与核心决策；
- 候选点、网格或服务节点之间的主要空间差异；
- 多项指标共同支持或相互矛盾的地方；
- 各候选方案更可能对应的客户、使用场景和履约机制假设；
- 对选址、布局、店型、容量、品类、产品方案、渠道和时段的具体影响；
- 候选方案优先级及其成立条件；
- 下一步踏勘、访谈、试点和直接数据验证计划。

数据健康、来源 ID、工具状态和技术参数继续保留在运行工件中供追溯，但不占据报告主体。

## 10. 验收标准

1. `catalog()` 保持 7 个轻量字段；
2. 54 个工具的 `detail()` 都能回答“测量什么、用于什么、怎么比、和什么一起解释、注意什么”；
3. `MetricDetail` 真正向 Agent 暴露 YAML 中已有的分析知识，而不是只返回输入输出和免责声明；
4. 用户给候选点时能生成同口径候选方案比较，只有区域时能生成内部空间单元比较；
5. 主 Agent 能围绕决策问题选择多项互补指标，而不是按数据类型拆章；
6. 结果能解释候选对象之间的差异、相互支持和冲突，不只是返回数值；
7. B2C 报告能形成店型、场景、选品和开业验证假设；
8. B2B 报告能形成目标账户、节点、产品方案、履约和投运验证假设；
9. 人口和夜光在数据可读且裁剪有效时，不因 `record_count = 0` 被误判不可用；
10. 报告以项目判断和行动为主体，不出现大段审计台账、规则清单或重复免责声明；
11. 对代理指标的边界采用简洁专业表达，不妨碍 Agent 给出有用分析；
12. 主分析师审校的是分析质量、机制和行动价值，而不是机械字段合规。
