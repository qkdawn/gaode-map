# 专业策划 PPT 生成能力设计草案

## 1. 背景与目标

当前系统已经具备区域空间分析能力，能够围绕一个已选区域形成范围、POI、H3 网格、人口、夜光、路网、共享网格和 Agent 总结等结构化结果。

下一阶段希望基于这些区域结果，生成类似城市更新、概念策划、招商研判类项目中的专业 PPT 成果。目标不是生成普通数据报表，也不是把现有总结小卡片简单导出，而是形成一份有叙事、有证据、有图片、有地图、有章节节奏，并且能够经过人工多轮调整后再定稿的策划型汇报材料。

本能力的第一阶段重点是生成可编辑的策划文档和逐页页面脚本，而不是直接生成最终 PPTX。前端如何从现有分析工作台过渡到 PPT 生成工作流尚未定稿，因此本文先沉淀输入、输出、流程和分阶段实现边界。

## 2. 核心原则

1. 不让 AI 直接自由生成 PPT 样式。
2. AI 先生成可编辑的策划文档和页面脚本。
3. 用户确认内容后，再由固定模板生成 HTML 幻灯片或 PPTX。
4. 页数、主题、受众、深度都属于配置项。
5. 所有事实必须来自区域数据、附件或联网资料。
6. 附件上传是独立入口，PPT 生成流程只消费已上传素材。
7. 联网资料必须带来源引用，不能作为无来源判断。
8. 前端承载方式待定，不在第一阶段强行改总结面板。

## 3. 用户流程

1. 用户选择一个已有分析区域。
2. 用户填写 PPT 生成配置，包括策划主题、页数、汇报类型、目标受众、生成深度、是否联网和使用哪些附件。
3. 系统整理输入包，包括区域分析数据、地图和图层快照、附件素材、联网研究资料。
4. AI 生成第一版策划文档和 page brief。
5. 用户和 AI 多轮沟通修改文档，包括改主题、改目录、改页数、改页面论点、指定图片、补充附件和调整引用。
6. 用户确认内容后，系统再进入最终生成阶段。
7. 最终生成 HTML 幻灯片或 PPTX。

这个流程的关键点是：最终页面生成之前，先让用户确认内容和页面脚本。AI 不直接跳到 PPTX，避免一次生成的结构、论点和视觉风格都不可控。

## 4. PPT 生成配置

PPT 生成配置应作为独立输入，而不是散落在提示词里。推荐字段如下：

| 字段 | 含义 | 默认建议 |
| --- | --- | --- |
| `theme` | 本次策划主题，由用户输入 | 空，由用户填写 |
| `deck_type` | 汇报类型，例如城市更新策划、商业选址研判、区域诊断报告 | `urban_renewal` |
| `page_count` | 目标页数，是配置项，不是固定值 | 15 |
| `depth` | 生成深度，例如快速简报、初步成果、完整汇报 | `brief` |
| `audience` | 目标受众，例如政府评审、招商方、内部研讨、课程展示 | `government_review` |
| `attachment_ids` | 本次使用的已上传附件 ID | 空数组 |
| `web_research` | 是否开启联网研究 | `true` |
| `visual_policy` | 图片使用策略，例如优先附件图、优先地图快照、缺图时输出图片需求提示 | `prefer_attachment` |

配置 schema 可以表达为：

```json
{
  "theme": "用户输入的策划主题",
  "deck_type": "urban_renewal | site_selection | area_diagnosis",
  "page_count": "number",
  "depth": "brief | preliminary | full",
  "audience": "government_review | investment | internal | education",
  "attachment_ids": ["attachment_id"],
  "web_research": true,
  "visual_policy": "prefer_attachment | prefer_map_snapshot | prompt_when_missing"
}
```

其中 `page_count` 的默认值可以是 15，但实现和提示词都不能把 15 页写死。

## 5. 页数配置规则

页数影响目录深度和叙事密度，应由配置驱动。

| 页数范围 | 适用形态 | 叙事重点 |
| --- | --- | --- |
| 6-10 页 | 区域诊断简报 | 快速说明范围、关键数据、核心判断和下一步 |
| 11-18 页 | 策划简报 | 默认推荐形态，覆盖背景、研判、定位、策略和下一步 |
| 19-30 页 | 初步成果汇报 | 增加案例、竞品、功能分区、运营路径和阶段策略 |
| 30 页以上 | 完整成果汇报 | 需要用户先确认章节目录或参考目录 |

当 `page_count` 采用默认值 15 时，可以使用本文第 10 节的默认结构。若用户选择其他页数，系统应先根据配置动态生成目录，再进入 page brief 生成。

## 6. AI 输入包

AI 输入应被整理为稳定的证据包，而不是把所有原始数据直接塞进提示词。

### 6.1 区域数据

区域数据来自当前分析工作台已有结果，主要包括：

- 分析范围、等时圈或绘制区域。
- POI 总量、分类结构、主导业态和数据来源。
- H3 网格分析、热点、冷点、空间集聚和机会格。
- 人口总量、密度、年龄结构、性别结构和客群线索。
- 夜光总量、均值、P90、点亮率、热点和夜间活力判断。
- 路网节点、边、道路长度、空间句法指标和可达性判断。
- POI、人口、夜光等多维共享网格耦合结果。
- 前端结构化分析摘要。

### 6.2 视觉素材

视觉素材是专业 PPT 的关键输入，应与文本证据分开管理。

可用素材包括：

- 当前地图总览快照。
- POI 图层快照。
- H3 网格图层快照。
- 人口图层快照。
- 夜光图层快照。
- 路网图层快照。
- 用户上传的现场图片、规划图、效果图、参考 PPT 页面、项目照片。

AI 不应直接决定最终排版，但可以在 page brief 中声明某页需要使用哪个素材，或者说明缺少哪类素材。

### 6.3 附件素材库

附件上传是独立入口。PPT 生成流程只消费已上传和已解析的附件。

附件解析后应整理为素材库，而不是只作为聊天附件存在。建议分为：

- `text_evidence`：政策、历史、定位、案例、说明文字。
- `visual_assets`：现场照片、效果图、地图、参考页截图。
- `data_tables`：人口、消费、租金、竞品、业态等表格。
- `style_reference`：参考 PPT 的版式、标题层级、色彩、图文节奏。

每个素材至少记录：

- 素材 ID。
- 来源文件名。
- 页码或图片编号。
- 素材类型。
- 简短摘要。
- 适用页面或适用章节。
- 来源可信度。
- 是否必须引用。

AI 在输出中引用素材 ID，例如“使用 `asset_012` 作为红砖建筑外立面图片”，最终由模板系统插入真实图片。

### 6.4 联网研究

联网研究默认开启，但必须可追溯。

联网资料应包含：

- URL。
- 标题。
- 发布日期或访问日期。
- 摘要。
- 可支持的页面或论点。
- 证据用途。

联网内容主要用于：

- 城市背景。
- 政策背景。
- 商圈资料。
- 人口和消费资料。
- 城市更新、文旅、商业策划案例。
- 竞品或周边项目参考。

联网资料不能替代本地分析结果，也不能覆盖附件中的明确项目事实。

## 7. 联网与附件的证据优先级

建议证据优先级如下：

1. 用户明确上传的项目资料。
2. 当前区域分析产生的结构化数据。
3. 用户上传的参考 PPT 和现场素材。
4. 带来源的联网资料。
5. AI 的归纳、类比和策划表达。

其中第 5 类只能用于组织表达和形成策略推演，不能作为事实来源。

## 8. AI 输出：deck brief

AI 第一阶段输出 `deck_brief`，不是 PPTX 文件。

推荐输出结构：

```json
{
  "deck_config": {},
  "deck_outline": [
    {
      "section": "章节名称",
      "page_range": "页码范围",
      "purpose": "章节目的"
    }
  ],
  "pages": [
    {
      "page_no": 1,
      "section": "章节名称",
      "title": "页面标题",
      "claim": "本页核心判断",
      "body_points": ["页面要点"],
      "evidence_refs": ["证据引用"],
      "asset_refs": ["素材引用"],
      "image_prompt": "缺少图片时需要补充的图片需求提示",
      "layout_hint": "建议版式",
      "missing_inputs": ["待补充资料"]
    }
  ],
  "source_bibliography": [
    {
      "source_id": "来源 ID",
      "title": "来源标题",
      "url": "来源链接",
      "used_for": "使用位置"
    }
  ],
  "revision_notes": ["本轮修改说明"]
}
```

`image_prompt` 的作用不是生成最终图片，而是告诉用户或后续素材系统：这一页需要什么内部图片、现场图、地图或效果图。

## 9. 人工迭代机制

第一阶段的交互对象是文档和 page brief。

用户可以逐轮提出：

- 改主题。
- 改页数。
- 改目录。
- 删除某页。
- 增加某页。
- 强化某类证据。
- 指定使用某个附件图片。
- 要求联网补充某类资料。
- 调整汇报对象和表达口吻。

每轮 AI 应输出：

- 更新后的目录。
- 更新后的页面脚本。
- 修改摘要。
- 仍缺失的素材或资料。
- 需要用户确认的问题。

只有当用户确认“内容定稿”后，才进入最终页面渲染。

## 10. 默认 15 页结构

当 `page_count` 使用默认值 15 时，可以采用以下结构：

1. 封面：项目名、区域、策划主题、日期。
2. 破题：这个区域要解决什么更新命题。
3. 区位与范围：地图、等时圈、核心影响范围。
4. 历史与文化线索：来自附件和联网资料。
5. 当前空间格局：H3、路网和范围结构。
6. POI 与业态结构：供给、主导业态和缺口。
7. 人口与客群基础：常住、年龄和画像。
8. 夜光与活力：夜间经济活动和热点。
9. 商圈、竞品和外部环境：联网和附件补充。
10. 核心诊断：优势、短板和机会。
11. 策划定位：一句话定位和关键词。
12. 场景策略：文化、消费、社交、产业等场景。
13. 空间更新建议：功能分区、动线和节点。
14. 运营与招商方向：人群、业态、活动和节奏。
15. 结论与下一步：需要补充的数据和落地路径。

该结构只是默认模板。实际页数和章节应由 `page_count`、`deck_type`、`depth` 和 `theme` 动态决定。

## 11. 前端承载待定

当前不急着确定最终放在哪里。

可能方案包括：

1. 独立“PPT 策划生成”工作区。
2. Agent 总结面板中的新标签页。
3. 历史记录详情中的“生成策划 PPT”入口。
4. 先只生成文档，后续再接 HTML 幻灯片预览。

第一阶段建议先做文档生成和迭代，不强行改总结面板。这样可以避免在前端承载方式未定时，把能力耦合到现有总结面板里。

## 12. 分阶段实现计划

### 第一阶段：策划文档生成

目标：

- 支持 PPT 生成配置。
- 支持当前区域数据输入。
- 支持选择已上传附件。
- 支持联网资料引用。
- 输出可编辑 deck brief。

不做：

- 不直接生成 PPTX。
- 不强行改总结面板。
- 不做复杂前端翻页。

### 第二阶段：页面脚本确认

目标：

- 用户可以逐页修改。
- 用户可以调整页数和目录。
- 用户可以指定图片和素材。
- 用户可以查看引用来源。

### 第三阶段：HTML 幻灯片预览

目标：

- 用固定模板渲染 page brief。
- 支持专业汇报风视觉。
- 支持地图和附件图片插入。
- 保留来源引用和缺口提示。

### 第四阶段：PPTX 导出

目标：

- 将确认后的 HTML 或结构化页面导出为 PPTX。
- 保持模板一致性。
- 避免 AI 直接随机排版。

## 13. 验收要点

- 文档阶段可以在不生成 PPTX 的情况下完成。
- 页数由配置控制，不硬编码为 15。
- 附件上传保持独立，本流程只消费已上传附件。
- 联网事实必须带来源引用。
- deck brief 中每页都有标题、核心判断、证据、素材需求和缺口提示。
- 前端承载方式明确标注为待定。
- 第一阶段明确是生成文档和 page brief，不直接生成 PPTX。

## 14. 当前结论

专业 PPT 生成不应从“AI 直接做 PPT”开始。

更稳的路线是：

区域数据 + 附件素材 + 联网资料 -> AI 生成策划文档和逐页页面脚本 -> 人工多轮确认 -> 固定模板生成 HTML 或 PPT。

这样既能保证专业感，也能避免一次性做太大、样式不可控、事实来源不清和前端承载过早绑定的问题。
