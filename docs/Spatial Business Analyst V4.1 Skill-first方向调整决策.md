# Spatial Business Analyst V4.1：Skill-first 方向调整决策

> **状态：方向已确认，核心收敛已完成**
>
> **决策日期：2026-07-17**
>
> **适用范围：** `spatial-business-analyst` 的 Agent 协作方式、专业任务分派、章节交付、总编审校与报告组装。
>
> **决策优先级：** 本文对“Agent 如何协作和运行”具有优先解释权。既有《Spatial Business Analyst V4.1 分析智能、指标知识与数据健康改造草案》继续作为业务理解、指标知识、项目内部比较、数据健康和报告目标的设计背景。

## 1. 决策摘要

Spatial Business Analyst V4.1 的执行主体调整为 **Codex 主 Agent 与其原生 Subagent 协作能力**。

后续不再把 Python 应用代码建设成另一套 LLM Agent 运行时。项目代码不负责模拟专业作者、总编或 Codex 的任务调度能力，而是向 Codex 提供真实项目数据、空间指标、稳定工具接口、结构化工件校验、确定性报告编译和不可变运行存储。

目标链路收敛为：

```text
Codex 主 Agent 理解项目与决策问题
→ 规划专业任务及依赖
→ 按依赖波次原生分派专业 Subagent
→ 专业 Subagent 交付结构化 ChapterDeliveryPackage
→ 主 Agent 验收并按需退回原作者一次
→ 总编基于 accepted 交付进行受约束综合
→ Python 校验并确定性编译报告
→ 保存 V4.1 不可变 run
```

这次调整不降低 V4.1 的分析要求，而是把智能协作放回最适合承担它的 Codex，把数据、空间计算、契约和编译留在最适合承担确定性的领域代码中。

## 2. 为什么改变方向

### 2.1 Codex 已经提供 Agent 协作基础设施

Codex 原生具备专业 Subagent 分派、并行执行、Agent 复用、消息传递和上下文控制能力。继续在 Python 中实现 Provider 协议、Prompt phase、异步波次调度、作者循环和编辑循环，会重复建设 Codex 已经拥有的能力。

V4.1 需要定义的是“专业任务应如何拆、输入什么、交付什么、如何验收”，而不是重新实现一个通用 Agent 框架。

### 2.2 双运行时会造成契约漂移

如果 Codex Skill 和应用内 LLM 编排器同时拥有项目理解、任务规划、作者 Prompt、退修和总编逻辑，就会形成两条行为相近但难以保持一致的运行链路：

- Skill 更新后，Python Prompt 可能仍遵循旧规则；
- Python Schema 更新后，Codex 分派模板可能没有同步；
- 同一个角色在两条链路中可能获得不同材料或产生不同交付；
- 测试容易验证 Provider mock，而不是验证真实项目分析是否有决策价值。

Demo 阶段不应维护这种双路径，也不应为尚未确认的应用内自动写作能力保留兼容层。

### 2.3 自建调度会把复杂度放错位置

DAG 依赖、并行波次、定向退修和 Agent 复用是协作策略。若将其实现为 Python 中的通用调度器，领域模块就需要知道 Provider 状态、Prompt 格式、Agent 生命周期、进度事件和失败恢复等大量非空间分析知识。

这违反了项目“复杂度下沉但职责不混淆”的原则：空间领域模块应隐藏数据和算法复杂度，而不是吸收 Agent 平台复杂度。

### 2.4 自由章节写作不能稳定产生决策价值

让专业 Agent 直接“写一章”容易产生以下问题：

- 指标和事实被写成连续散文，缺少清楚的比较基准；
- 行动建议与前文 finding 之间没有可验证的推导关系；
- 总编只能从正文中二次猜测决策表；
- 缺少数据时容易出现泛化建议或未经验证的经营判断；
- 章节篇幅增长，但负责人仍看不到下一步应做什么、如何验证、何时停止。

因此，专业 Agent 应首先交付结构化判断包。最终报告的章节和表格由 accepted 交付包稳定组装，而不是依赖总编重新解释或改写专业正文。

## 3. 保留的 V4.1 能力

方向调整保留以下 V4.1 核心设计：

1. **项目商业理解：** 判断 B2C、B2B 或 mixed，识别付款方、使用者、需求单位、履约方式和当前决策。
2. **指标知识卡：** 保留轻量 `catalog()` 与详细 `detail(tool_id)`，帮助 Agent理解指标测量内容、适用问题、比较方式、组合解释和误读边界。
3. **项目内部比较：** 有候选对象时使用同口径范围比较；只有项目区域时使用合理的内部空间单元比较。
4. **真实数据分析：** 继续使用保存的项目材料、POI、H3、规则网格、人口、夜光、路网、等时圈和其他可用分析结果。
5. **数据健康下沉：** 可读取性、空间相交、有效单元、NoData、年份、几何和字段健康由所属领域模块处理。
6. **精简公开工件：** 继续保存 source index、分析计划、章节版本、编辑审校、最终报告和 SVG 资产。
7. **受约束综合：** 总编可以形成执行摘要、跨章结论、最终建议和章节衔接，但只能引用 accepted 专业交付。
8. **决策表：** 最终报告继续包含“关键空间证据与行动”和“分期行动与验证闸门”。

## 4. 明确不恢复或不继续建设的内容

### 4.1 不恢复 V3 治理工件

本次调整不恢复：

- Analysis Blueprint 锁；
- 证据快照；
- 证据执行谱系；
- 审计台账；
- 章节包审计附录；
- V3/V4 双路径；
- 旧字段 fallback 和兼容读取。

V3 仅可作为专业角色分工和依赖协作的行为参考，不重新暴露其 artifact 契约。

### 4.2 Python 不再承担 LLM Agent 运行时

后续停止扩展并逐步移除以下应用内编排职责：

- LLM Provider 驱动的专业作者；
- LLM Provider 驱动的总编；
- 作者和编辑 Prompt phase 协议；
- Python `asyncio` 波次调度器；
- Python 中的 Agent 消息总线和生命周期管理；
- Python 中的退修循环和原作者模拟；
- 为 LLM 写作构造的完整运行时投影对象；
- 依赖 Provider mock 才能验证的报告生成主链路。

如果未来产品确实需要“应用内一键自动生成完整报告”，应将其作为单独的产品能力重新设计，而不是与 Codex Skill 共享一个名称却维护两套隐含行为。

## 5. 目标职责边界

| 责任 | Codex / Skill 控制面 | Python / 领域数据面 |
| --- | --- | --- |
| 项目理解 | 判断商业模式、决策问题、假设和专业责任 | 读取并规范化项目材料、范围和已有结果 |
| 任务规划 | 生成专业任务、角色和依赖 DAG | 校验计划结构、章节 ID 和依赖合法性 |
| 专业分派 | 使用 Codex 原生 Subagent，按波次并行分派 | 不创建或调度 LLM Agent |
| 上下文控制 | 只向角色提供被授权的材料、指标和必要上游输出 | 提供稳定资源 ID、结果 ID 和可查询数据 |
| 指标选择 | 根据决策问题读取知识卡并组合指标 | 提供 `catalog/detail/execute` 和结果复用 |
| 空间计算 | 解释空间结果与项目影响 | 负责范围归一化、算法执行、数据健康和稳定输出 |
| 专业交付 | Subagent 输出 `ChapterDeliveryPackage` | 校验结构、引用和确定性约束 |
| 质量审校 | 接受、定向退修一次或失败 | 执行可自动验证的引用和一致性检查 |
| 跨章综合 | 只基于 accepted 章节写受约束综合 | 校验综合引用均指向 accepted 章节 |
| 报告生成 | 决定发布内容和顺序 | 确定性渲染章节、决策表和验证闸门 |
| 运行保存 | 确认交付完成 | 保存不可变 V4.1 run 和公开白名单工件 |

这条边界的核心原则是：**判断与协作由 Codex 承担，数据与确定性由代码承担。**

## 6. Codex Skill 的主 Agent 工作流

Skill 应将以下流程定义为唯一协作方式。

### 6.1 理解项目

主 Agent 首先读取用户问题、项目材料、空间范围和已有结果，明确：

- `business_model`；
- `primary_customer_or_account`；
- `demand_unit`；
- `fulfillment_model`；
- `candidate_targets`；
- 当前必须推动的商业或空间决策；
- 需要验证的 `decision_hypotheses`。

缺少可识别范围、决策问题或必要项目材料时，应停止专业分派并返回明确补齐动作。

### 6.2 规划专业任务

主 Agent 按判断责任生成 3–6 个专业任务，不按人口、POI、夜光或路网等数据类型机械拆章。

可选角色包括但不限于：

- 商业模式分析；
- 空间结构分析；
- 可达性与服务范围分析；
- B2C 场景、店型和产品分析；
- B2B 账户、节点和履约分析；
- 文旅空间策划；
- 现场验证与试点设计。

角色根据项目问题动态选择，不要求每次全部启用。

### 6.3 按依赖波次分派

主 Agent 使用 `context`、`finding` 和 `decision` 三类依赖表达任务关系：

- `context` 提供背景、对象、比较口径、事实和代理边界；
- `finding` 进一步提供空间发现、可能机制、项目影响和不确定性；
- `decision` 只有上游任务被 accepted 后，才提供行动及验证或停止条件。

无必要依赖的任务使用 Codex 原生 Subagent 在同一波次并行执行。下游任务只获得依赖边要求的上游内容，不获得所有已完成章节。

### 6.4 验收和退修

主 Agent 对每个专业交付只能作出：

- `accepted`；
- `revision_required`；
- `failed`。

需要退修时，应向同一个专业 Agent 提供定向指令，说明缺少的证据、比较、推导、行动或验证条件。同一任务最多退修一次；第二次仍不合格即失败。总编不得生成替代专业交付。

### 6.5 受约束综合与组装

只有 accepted 专业交付可以进入最终报告。总编可以形成：

- 执行摘要；
- 跨章结论；
- 最终建议；
- 章节衔接。

每条综合内容必须绑定其引用的 accepted `chapter_ids`。总编不得新增专业 Agent 未提出且证据未支持的判断，也不得静默改写已接受结论。

## 7. 专业 Subagent 输入契约

专业 Subagent 只接收完成当前责任所需的角色专属输入：

```yaml
ChapterAssignment:
  chapter_id:
  specialist_role:
  decision_question:
  project_understanding:
  authorized_resource_ids:
  authorized_project_materials:
  metric_knowledge_cards:
  available_metric_results:
  comparison_design:
  upstream_dependencies:
  dependency_boundaries:
  revision_instructions:
```

输入契约遵循以下原则：

- `authorized_resource_ids` 是材料授权边界；
- 只提供与本章判断有关的项目材料和指标知识卡；
- 只提供本章需要的已执行结果，不提供完整运行台账；
- 只提供依赖边要求的上游内容，不提供所有章节全文；
- 非必要依赖尚不可用时，明确注入边界说明；
- 退修时只增加定向退修指令和必要的新上游信息；
- 不向专业 Agent 提供完整 `source-index.json`、无关文档、Provider 日志或其他角色的完整工作过程。

这是专业任务的协作协议，而不是要求 Python 重新建设上下文安全沙箱。

## 8. 专业交付契约

专业 Agent 不再自由提交一篇不可校验的章节散文，而是交付结构化 `ChapterDeliveryPackage`：

```yaml
ChapterDeliveryPackage:
  chapter_id:
  specialist_role:
  decision_question:
  status: ready | blocked
  findings:
  decision_tables:
  actions:
  validation_conditions:
  evidence_links:
  limitations:
  unmet_dependencies:
```

核心字段含义如下：

- `decision_question`：本交付负责回答的项目决策问题；
- `findings`：空间现象、多指标支持或冲突、可能机制及项目影响；
- `decision_tables`：专业角色直接提供的比较、进入条件、行动或验证表；
- `actions`：由 findings 推出的具体项目动作；
- `validation_conditions`：现场、访谈、试卖、询价、订单或成本验证，以及继续、调整和停止条件；
- `evidence_links`：本交付实际使用的授权项目材料和空间结果；
- `limitations`：数据缺口、代理边界和未解决的不确定性；
- `unmet_dependencies`：当前未满足但不妨碍有限交付的依赖，或导致 blocked 的必要依赖。

后续 Schema 设计应确保 finding、action 和 validation condition 具有稳定 ID，使行动能够明确引用其来源 finding，而不是依赖总编从散文中猜测推导关系。

## 9. 专业质量门槛

主 Agent 和确定性校验器共同执行以下门槛。

### 9.1 证据

- 核心 finding 必须关联真实且已授权的 evidence link；
- 引用的资源和结果必须实际存在；
- 人口、夜光、POI、路网和等时圈等代理信号必须明确其代理性质；
- 缺少数据时必须声明缺口，不得补造数值或事实。

### 9.2 比较

- 指标差异必须说明比较基准；
- 多候选对象必须使用同一出行方式、时间阈值、半径或其他一致口径；
- 单一区域必须说明内部比较单元、数据年份、分辨率和参数；
- 项目内部相对差异不得被描述成外部市场排名或经营预测。

### 9.3 推理

- 区分 fact、proxy、inference 和 recommendation；
- 关键机制优先由互补指标或项目材料共同支持；
- 冲突信号必须解释或转化为待验证问题；
- 单一代理指标不得生成商业总分、消费判断或成功概率。

### 9.4 行动

- action 必须由一个或多个 finding 推出；
- 行动应具体到候选点、布局、店型、容量、产品、服务、节点、路径、履约或验证；
- 不接受与前文判断无关的通用咨询建议。

### 9.5 验证

- 客流、消费、营收、订单、成本、ROI 和因果效果需要直接经营数据；
- 没有直接数据时，应形成具体的踏勘、访谈、试卖、询价或订单验证；
- 验证应尽量包含通过、调整或停止条件。

未满足要求时，只退回对应专业 Agent，不允许总编代写修复。

## 10. Python 领域能力的保留方向

Python 代码继续提供以下深模块能力：

1. **项目输入准备：** 读取项目文档、空间范围、数据版本和已有分析结果。
2. **指标发现与知识：** 提供轻量目录和详细指标知识卡。
3. **指标执行：** 规范化范围、运行真实空间计算、复用已有结果并返回稳定 result ID。
4. **数据健康：** 在所属空间模块中处理栅格、表格、矢量和路网健康问题，只向 Agent 暴露可用性及其影响。
5. **工件校验：** 校验计划 DAG、授权引用、finding/action 关系、accepted 引用和公开契约。
6. **报告编译：** 直接渲染 accepted `ChapterDeliveryPackage`、专业决策表和总编受约束综合，不调用 LLM，不改写专业判断。
7. **运行存储：** 保存不可变 V4.1 run，并限制公开工件类型。

公开工件继续保持：

```text
source-index.json
analysis-plan.json
chapters/<chapter-id>.v1.json
chapters/<chapter-id>.v2.json
editorial-review.json
report/project-report.md
report/assets/*.svg
```

## 11. 迁移原则

本轮收敛已按以下阶段完成，后续仅在同一职责边界内迭代：

### 阶段一（已完成）：建立 Skill 协作契约

- 重写 Skill 主流程；
- 增加专业角色、任务输入、章节交付和质量门槛 references；
- 明确 Codex 原生并行、依赖释放、Agent 复用和一次退修行为。

### 阶段二（已完成）：收敛公开工件契约

- 将自由章节交付收敛为 `ChapterDeliveryPackage`；
- 保留分析计划、依赖关系和 accepted 综合引用；
- 让决策表直接来自专业交付，而不是从章节散文二次抽取。

### 阶段三（已完成）：收缩 Python 编排代码

- 移除 Provider 驱动的规划、作者和编辑职责；
- 移除 Python 自建波次调度和退修循环；
- 保留数据工具、Schema 校验、编译和存储；
- 不保留新旧双路径或旧字段 fallback。

### 阶段四（已完成）：真实项目验收

- 使用真实保存项目数据创建新的不可变 run；
- 检查专业角色是否收到最小必要上下文；
- 检查交付是否包含比较基准、证据、行动和验证条件；
- 检查最终报告是否稳定产生有价值的决策表；
- 检查总编没有替换专业判断；
- 检查公开目录中没有恢复 V3 工件。

## 12. 验收标准

本方向当前实施结果应持续满足：

1. Codex Skill 是专业协作流程的唯一来源，不再与 Python LLM 编排器维护双路径。
2. 无依赖专业任务由 Codex 原生并行分派，退修发送给同一个专业 Agent。
3. 专业 Agent 只获得角色授权输入，不接收完整运行上下文和无关章节。
4. 专业交付使用结构化 `ChapterDeliveryPackage`，而不是不可追溯的自由章节正文。
5. finding 有真实证据和比较基准，action 可追溯到 finding，经营缺口被转化为验证条件。
6. 总编只接受、退修或失败，并且综合内容只引用 accepted 章节。
7. Python 不调用 LLM 生成、改写或替换专业判断。
8. 最终报告直接从 accepted 交付编译，稳定保留“关键空间证据与行动”和“分期行动与验证闸门”。
9. 真实数据、指标知识、数据健康、结果复用和不可变 run 能力继续工作。
