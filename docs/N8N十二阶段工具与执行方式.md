# N8N 动态决策研究与证据工具执行方式

## 1. 当前链路

当前工作流不再把十二个常见分析方向固定成十二章，也不为每个方向维护一套 Agent。

```text
项目问题与项目上下文
→ 规划 Agent 生成动态 decision_units
→ 针对当前 decision_unit 运行证据路由 Agent
→ N8N 串并行执行证据工具
→ 研究分析 Agent 生成 decision_memo
→ 所有决策单元完成
→ 跨单元综合 Agent 生成 report_blueprint
→ 统一写作 Agent 按蓝图逐节写作
→ 全局编辑、图件、报告装配与投递
```

十二个常见方向只作为规划 Agent 的思考启发：政策与场地、区域角色、市场与空间流向、供给缺口、客群与使用、主题资源、定位、产品、空间、运营、财务和分期。规划 Agent 可以合并、跳过、改写或增加项目特有问题。

## 2. 两个动态数量

### 2.1 决策单元数量

`decision_units` 的数量由规划 Agent 根据项目问题决定，不固定为三，也不固定为十二。每个单元只承担一个会改变后续选择的新判断：

- `unit_id`：稳定的单元标识。
- `title`：面向人的短标题。
- `question`：当前要回答的决策问题。
- `depends_on`：必须先成立的前序单元。
- `decision_output`：本单元独占的判断产物。
- `evidence_focus`：需要了解的事实，不预先指定工具。

依赖必须指向前面已经出现的单元。工作流只校验必填结构、ID 和依赖顺序，不用代码判断 `decision_output` 的语义是否重复，也不决定项目应该研究几个问题；单元之间是否拥有真正不同的新判断由规划 Agent 在输出前自检。

这里的“动态”有两个层次：规划 Agent 决定研究单元的语义和数量；N8N 只提供运行保护。当前 32 个单元是上下文和执行时间的异常保护上限，不是十二阶段模板，也不是要求每个项目必须拆成 32 个问题。超过上限时工作流直接报告规划超限并停止，不会静默截断或丢掉单元。

### 2.2 两个疑问的明确结论

**疑问一：动态决策单元变化后，工具 Agent 是否要修改？要，但只修改它的输入和路由职责。**

规划 Agent 生成的每个 `decision_unit` 都必须进入证据路由 Agent 的输入。路由 Agent 至少读取：当前单元的问题、它要产生的 `decision_output`、前序单元的 `decision_memo`、已有事实目录、当前工作简报和剩余工具预算。这样它才能判断哪些事实已经成立、哪些证据仍缺，以及哪些请求可以并行。

这不意味着为每个单元创建一个新的工具 Agent，也不意味着把“第几阶段调用哪个工具”写进代码。工具 Agent 只负责把当前研究问题翻译成一至三个合法、参数完整的工具请求；空间、文献、项目文档和互联网工具仍然是通用事实接口。研究 Agent 取得结果后可以自由分析、比较和形成判断，不能被路由 Agent 的 JSON、并行数量或工具预算限制表达能力。

**疑问二：具体有几个决策单元？由 AI 根据项目决定，不固定。**

这里要区分四个数量，它们互不等价：

| 数量 | 谁决定 | 含义 |
| --- | --- | --- |
| `decision_units` | 规划 Agent | 本项目真正需要回答的决策问题数量，可以合并、跳过或增加，不固定为三或十二。 |
| `next_tools` | 证据路由 Agent | 当前单元下一批需要取证的请求，最多三个；只是执行批次，不是研究单元数量。 |
| `tool_call_limit` | 工作流运行保护 | 单次运行最多的工具请求数，防止无限循环；不是要求项目完成多少次取证。 |
| `report_blueprint.sections` | 综合 Agent | 最终报告节数量，可少于、等于或多于决策单元数量。 |

当前实现中的 `maxItems: 32` 只是一条异常保护边界，用于拒绝失控的规划输出，不是业务模板、默认数量或静默截断规则。项目正常情况下可以是 2、3、5 或其他数量；如果规划确实超过保护边界，工作流应明确失败并要求重新规划，不能把它当成“自动完成 32 个单元”。同理，单批最多三个工具请求和总调用预算只限制取证执行，不限制研究 Agent 的推理深度。

工具调用预算与决策单元数量是两套独立的运行约束。预算不足时，工作流不得删除、合并或跳过规划出的单元，也不得把“没有继续调用工具”伪装成“证据已经充分”；应把该单元标记为证据预算耗尽，并让研究 Agent 在备忘录中明确当前可回答范围和缺口。预算策略可以按任务规模调整，但不能成为规划 Agent 的隐性章节模板。

### 2.3 报告节数量

决策单元数量不等于报告章节数量。跨单元综合 Agent 根据论证关系生成 `report_blueprint`：

- 多个相近决策单元可以合并为一个报告节。
- 一个复杂决策单元可以拆成多个报告节。
- 每节声明自己负责的新结论、必须保留的数字和具名对象，以及后文不得重复证明的内容。

因此，最终报告节数可以少于、等于或多于决策单元数。

## 3. 证据路由 Agent

证据路由 Agent 必须随动态决策单元调整。它每轮接收：

- 当前 `decision_unit`；
- 当前单元依赖的 `decision_memo`；
- 其他前序单元的最小事实目录；
- 当前 `working_research_brief` 和最近工具结果；
- 可用项目文档、空间指标目录和剩余调用预算。

它只输出 `continue` 或 `finish`，不负责研究结论和报告写作。`continue` 时选择一至三个参数已经确定且相互独立的工具请求；`finish` 时返回空数组。

路由 Agent 自主判断当前证据是否足够、应选择哪类证据、聚合空间结果是否需要继续 `inspect`、哪些请求可以并行，以及哪些请求必须等待上一结果后再构造参数。

代码只执行契约、权限、参数、重复请求、并行数量和预算校验。空间工具本身不返回“下一步查什么”。

## 4. 四类证据工具

### 4.1 空间数据库

`analyze_spatial_evidence` 提供七种通用分析语义：

1. `scope`：当前范围汇总；空指标时用于发现可用指标。
2. `accessibility`：调用 Valhalla 生成当前保存等时圈阈值内的嵌套时间圈并分层比较；当前 15 分钟步行等时圈默认分为 0–5、5–10、10–15 分钟。
3. `direction`：按八方向比较。
4. `neighborhood`：查看目标单元的邻域。
5. `rank`：按一个指标排序。
6. `relationship`：比较两至四个指标的共同高值、共同低值和信号冲突。
7. `inspect`：展开具体记录，并在网格或 H3 场景中返回具名 POI、相交道路和邻近具名对象。POI 包含名称、类别、细分类别、地址、直线方位距离和方向；道路包含名称、等级、空间关系及数据目录登记的受限指标，即使道路由网格检查自动展开，也不要求路由 Agent 预先枚举道路指标。

`accessibility` 不再使用项目中心到单元中心的直线距离分带。工具以当前保存等时圈作为最大范围，使用同一项目锚点、出行方式和 Valhalla 成本模型一次取得各级 contour，再按空间单元代表点落入的最小 contour 分组。无法由 Valhalla 完整生成或无法归入时间层的单元明确记为未分类，不使用圆形 buffer 或直线距离回退。高亮记录中的 `straight_line_distance_m` 只用于方位识别；`travel_time_band_min` 和 `travel_time_upper_bound_min` 才表示 Valhalla 等时圈层，不能混用，也不伪造单元的精确导航分钟数。

工具只返回受限事实，不返回几何、数据库连接、本地路径或研究建议。

### 4.2 文献知识库

`search_literature_evidence` 使用现有 GraphRAG 派生索引：

- `focused`：快速返回相关 PDF 原文证据。
- `synthesis`：需要跨文档机制归纳时执行完整综合。

文献库用于规范、研究方法和跨案例机制，不与实时互联网搜索合并。

### 4.3 项目文档

`read_project_document` 由 Docling 解析并分页读取项目原文。工作流只把轻量文档目录交给路由 Agent；路由 Agent 判断当前单元需要项目事实时读取首段，并在结论依赖后文时根据 `next_start_block` 发起下一轮读取。项目文档调用与其他证据工具使用同一预算、去重和过程保存机制。

前序决策不再通过 `read_previous_chapter` 读取。必要的前序 `decision_memo` 已直接进入当前路由和研究上下文。

### 4.4 互联网

- `search_public_web`：发现当前公开网页，只产生线索。
- `fetch_public_web_page`：读取准备使用的网页正文。

依赖搜索结果 URL 的全文读取必须放在下一轮。

## 5. 串并行规则

同一轮最多执行三个相互独立的请求。例如项目文档首段、空间排序和 focused 文献检索可以并行。

只有后一个请求的参数需要从前一个结果取得时才跨轮串行：

- `search_public_web → fetch_public_web_page`
- 文档当前页 → 下一页
- 尚不知道指标时，先 `scope` 发现指标，再构造具体空间分析
- 需要使用聚合结果中的 `record_ref` 时，先执行相应分析，再构造 `inspect`

如果指标 ID 或 `record_ref` 已经由当前输入和既有证据明确给出，就不存在上述依赖。代码不规定 `relationship`、`rank` 或任何其他模式之后必须调用 `inspect`。

一项失败不丢弃同批成功结果。结果按请求顺序合并，不按完成时间合并。调用总预算按实际请求数计算。

工具预算、上下文预算、连续无新证据或连续工具错误只结束当前单元的取证循环。N8N 保存明确的 `stop_reason`，不再额外请求路由模型确认结束，随后仍启动研究 Agent，按已经取得的证据形成尺度相称的 `decision_memo`；这些运行边界不能跳过当前单元，也不能阻止后续单元执行。

## 6. 研究与写作分离

工具获取结束后，研究分析 Agent 针对当前单元生成 `decision_memo`：

- `decision`
- `alternatives_considered`
- `reasoning`
- `key_facts`
- `named_entities`
- `implications`

它不生成正式章节，也不重新证明 `depends_on` 中已经成立的结论。

全部单元完成后，跨单元综合 Agent 才决定报告论证结构。统一写作 Agent 按 `report_blueprint` 逐节写作，并保留蓝图指定的数字、POI、道路和空间关系。蓝图中的强制事实和具名对象必须能够回溯到该节 `source_unit_ids` 对应的 `decision_memo`，无法回溯的名称不会进入写作约束。每次写作只接收全篇总判断、当前章节责任、对应的完整 `decision_memo`、必须保留的事实和可引用但不能重复证明的前序结论；不接收完整蓝图或已经写好的前文章节。

装配后的全局编辑使用受限补丁契约。编辑 Agent 只能提出逐字删除的重复片段、过渡类型、标题调整和格式等价的术语统一，不能返回完整章节。删除片段必须在整份报告至少出现两次，而且每次补丁只删除一个副本；术语替换只能改变大小写、空格或标点。标题只能采用蓝图标题或进行字符格式规范。过渡正文由 N8N 根据前后章节标题生成，模型不能借过渡新增项目事实。代码逐项应用补丁；任何导致关键判断、数字或具名对象丢失的补丁都会被放弃并保留原文。

## 7. 上下文和过程数据

完整工具结果只在当前 N8N 执行过程的结果存储中短期保留，不合并进 `analysis_runs.decision_state`。每轮回到模型的是有字符预算的 `working_research_brief`、最近结果和最多二十条具名空间记录，而不是累计全部 `function_call_output`；租约刷新只更新时间，不复制研究正文。

成功完成后，持久状态通过白名单只保留研究框架、动态 `decision_units`、各单元 `decision_memo` 及最小来源元数据、报告蓝图、报告节和最终产物，不保留完整工具正文或嵌套执行状态。失败执行保留必要诊断用于短期排错，再由运行环境按清理策略删除。

## 8. 核心边界

- 决策单元数量由规划 Agent 决定。
- 报告节数量由跨单元综合 Agent 决定。
- 证据路由 Agent 只帮助更好地调用工具，不限制研究和写作 Agent 的分析能力。
- 工具负责返回事实，不决定研究方向。
- 同一事实源只保留一个权威来源；GraphRAG、摘要和索引都是可重建派生物。

## 9. 接下来按此顺序收尾

以下顺序把两个疑问落实为可验收的工程任务。先保证“谁决定单元数量、谁决定工具批次、谁负责分析”边界清楚，再跑真实链路；不要用扩大超时或增加兼容入口掩盖契约问题。

1. **锁定动态规划契约**：规划 Agent 输出 `research_frame` 和按依赖排序的 `decision_units`；校验 ID、依赖和字段完整性。队列只执行规划结果，不补齐、不重排、不静默截断。`32` 只作为异常保护上限，不是项目单元数量。
2. **同步共享工具路由 Agent**：同一个路由 Agent 接收当前单元、依赖备忘录、事实目录、工作简报和预算，自主返回一至三个独立工具请求；不为不同单元复制 Agent，也不预设“第几单元调用什么工具”。
3. **明确工具调用边界**：代码只校验工具权限、参数完整性、重复请求、依赖关系、并行数量和预算；不在工具或校验器里写“下一步研究策略”。空间指标数量、`record_refs` 和必填字段只用于拒绝非法请求。
4. **拆开单元数量与工具预算并补齐契约测试**：预算不足时保留未完成单元并写入明确状态，由研究 Agent 说明证据边界；同时覆盖 `continue/finish`、每批 1–3 个独立请求、依赖调用跨轮、部分失败保留成功结果和预算裁剪。测试要证明并行只发生在工具获取阶段，不限制研究 Agent 的推理和写作。
5. **保持四类工具为通用事实接口**：空间、文献、项目文档和互联网工具只负责事实返回。空间 `inspect` 提供 POI/道路名称、类别、地址、距离、方向和指标值；工具不返回“下一步建议”，不为每个决策单元复制接口。
6. **验证单元级研究闭环**：同一个研究分析 Agent 逐单元自由形成 `decision_memo`；后续单元消费必要的前序判断，但不重复证明已经成立的事实。单元数量由规划结果决定，不能用调用预算代替研究完成条件。
7. **验证动态报告结构和递进**：综合 Agent 根据备忘录生成 `report_blueprint`，决定单元合并、拆分和递进关系；写作 Agent 按蓝图分节成稿，每节声明新增判断、必须保留的数字和具名对象，避免重复使用同一批网格或比例。
8. **重新生成并部署正式 workflow**：运行 workflow renderer，检查节点顺序、状态回写、并行执行和成功清理，再执行 N8N bootstrap；确认运行中的 workflow 与源码一致。
9. **真实链路验收**：使用现有项目检查实际生成了几个动态单元、每个单元的路由批次、空间具名记录、前序备忘录传递、蓝图覆盖、逐节报告、数据库状态和飞书投递；失败时保留明确诊断，不把捕获错误当作成功。
10. **收尾过程数据**：成功执行只保留规划、`decision_memo`、蓝图、报告节和必要诊断；完整工具正文只在短期排错期保留，按既定清理策略删除。失败运行则保留足以定位问题的最小过程记录。
