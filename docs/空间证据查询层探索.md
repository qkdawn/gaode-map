# 多源空间证据查询层探索

> 文档状态：第一阶段已实现
>
> 适用范围：`/analysis` 当前范围数据源、Agent scoped dataset 工具和 EvidenceNode 证据链
>
> 关联文档：[当前范围数据源与 AI 检索设计](./当前范围数据源与AI检索设计.md)

## 1. 文档定位

本文记录当前对“当前范围数据查询工具”的产品和技术探索，不是通用 GIS 设计，也不是业务结论生成器。

它要解决的问题是：

> 给定当前分析范围、一个点或一个几何范围，Agent 能从当前范围数据源中找到空间上真正相关的 POI、H3、共享栅格、人口、夜光和路网记录，并说明这些记录为什么相关。

查询层只负责空间关系、数据记录和可复核证据。诸如“竞争激烈”“适合开店”“路网较弱”等业务判断，仍由分析 Skill 或报告模块完成。

### 1.1 已确定的设计决策

以下内容作为第一阶段实现约束，不再作为开放选项：

1. 保留 `list_scope_datasets`、`query_scope_dataset`、`aggregate_scope_dataset` 和 `read_scope_record` 四个工具，不为每类数据重复创建查询工具。
2. `query_scope_dataset` 增加可选 `spatial`，字段过滤、排序、分页保持现有契约。
3. H3 只表示 POI 相关 H3 分析；`poi_raster_grid` 必须迁移为独立 `current:dataset:poi_grid`。
4. 路网线段和路网聚合栅格分别使用 `current:dataset:road_edges`、`current:dataset:road_grid`。
5. 第一阶段使用 `at_point`、`nearest`、`within_distance`、`intersects` 四个关系；`covered_by` 在底层保留语义，但在覆盖率计算和聚合完成前不向 Agent 宣称可用。
6. 输入可以是 GCJ-02 或 WGS84；内部几何统一到 WGS84，距离、面积和长度必须在米制计算环境中得到。
7. 空间关系先于字段排序。`nearest` 使用真实几何距离并默认按 `distance_m` 升序，不能退化为指标排序或中心点距离。
8. 空间关系结果属于查询证据，不进入指标目录，也不新增“空间派生指标”。

## 2. 首要边界：H3 不等于栅格

这是后续实现必须保持的产品边界。

### 2.1 H3 的定义

H3 是 POI 相关分析使用的六边形空间索引和分析单元。当前 H3 主要承载：

- POI 数量和密度；
- POI 类别结构；
- POI 集聚、热点和局部空间关系；
- 与 POI 相关的 H3 指标和证据。

H3 当前不应被描述为人口、夜光或路网的通用格网。即使这些数据最终也表现为多边形，也不代表它们使用 H3，或能够共享 H3 的 `cell_id`、分辨率和指标含义。

### 2.2 栅格的定义

“栅格”是多个分析域可以使用的空间承载方式，不是一个单一数据集。当前除 POI 栅格外，还包括：

- 人口栅格；
- 夜光栅格；
- 路网聚合栅格；
- 未来可能增加的其他规则网格或栅格化结果。

这些栅格可能在分辨率、原点、范围、投影、统计口径和 `cell_id` 命名空间上不同。查询层不能因为它们都叫“栅格”就把它们当成同一套格网连接。

### 2.3 目标来源语义

来源 ID 应表达产品语义，而不是直接复用 artifact 类型。目标口径如下：

| 来源 ID | 几何 / 单元 | 主要内容 | 是否属于 H3 |
| --- | --- | --- | --- |
| `current:dataset:poi` | Point | 当前范围 POI 明细 | 否 |
| `current:dataset:h3` | H3 Polygon | POI 相关 H3 分析单元 | 是 |
| `current:dataset:poi_grid` | 规则栅格 Polygon | POI 栅格化结果 | 否 |
| `current:dataset:population` | 人口栅格 Polygon | 人口值、密度和人口估算 | 否 |
| `current:dataset:nightlight` | 夜光栅格 Polygon | 夜光强度及其统计 | 否 |
| `current:dataset:road_edges` | LineString | 路网线段及句法指标 | 否 |
| `current:dataset:road_grid` | 路网聚合栅格 Polygon | 道路长度和路网指标聚合 | 否 |

当前代码中的 `current:dataset:h3` 仍可能承接 `poi_raster_grid`，这是需要在后续实现中拆开的兼容问题，不能继续作为新的设计口径。

## 3. 查询层的产品边界

查询工具是 Agent 面向多源空间数据的统一证据检索层。Agent 不需要知道：

- POI 坐标是 `location` 还是 GeoJSON geometry；
- H3 是 index 还是 Polygon；
- 人口和夜光来自原始栅格还是已转成 Polygon；
- 道路是节点、边还是折线；
- 数据原始坐标是 GCJ-02 还是 WGS84；
- 数据最终保存于 `poi_results` 还是 `analysis_artifacts`。

统一的是查询意图和返回证据，不是强迫所有数据使用同一种底层算法。

## 4. 查询类型

空间问题先分成两类，不要让一个接口同时承担两种含义。

### 4.1 记录查询

回答“哪些记录与目标空间有关”：

- 这个点落在哪个人口、夜光或 POI 栅格；
- 这个点属于哪个 POI H3；
- 距离这个点最近的道路或 POI 是什么；
- 500 米内有哪些 POI；
- 哪些道路与研究范围相交；
- 哪些 H3 或栅格与等时圈相交。

第一阶段优先实现记录查询。

### 4.2 空间聚合

回答“这个范围总体怎么样”：

- 范围内有多少 POI；
- 范围涉及多少个 H3 或栅格；
- 人口按覆盖比例估算是多少；
- 夜光面积加权平均值是多少；
- 范围内道路总长度是多少。

聚合可以复用同一套空间底层，但必须单独保留 `aggregate` 语义，不能把一页记录的数量误当成范围总量。

## 5. 统一查询契约

记录查询保留现有 `filters`、`sort`、`limit`、`offset` 和 `year`，增加可选的 `spatial`。

### 5.1 点附近查询

```json
{
  "source_id": "current:dataset:road_edges",
  "spatial": {
    "relation": "nearest",
    "point": [112.98, 28.19],
    "coord_type": "gcj02",
    "max_distance_m": 80
  },
  "limit": 5
}
```

POI 的半径查询使用 `within_distance`；道路的最近查询使用真实线段；H3、人口和夜光栅格的点定位使用 `contains` 或面向 Agent 的 `at_point`。

### 5.2 范围查询

```json
{
  "source_id": "current:dataset:nightlight",
  "spatial": {
    "relation": "intersects",
    "geometry": {
      "type": "Polygon",
      "coordinates": [[[112.97, 28.18], [112.99, 28.18], [112.99, 28.20], [112.97, 28.20], [112.97, 28.18]]]
    },
    "coord_type": "gcj02",
    "min_overlap_ratio": 0.1
  },
  "limit": 20
}
```

### 5.3 查询目标类型

当前支持三种目标类型：

- `point`：一个坐标点；
- `geometry`：Point、Polygon、LineString 或 Multi* GeoJSON；
- `record`：通过 `source_id + record_id` 找到一个已有记录作为目标；同源查询默认排除目标自身，可通过 `exclude_target` 调整。

目标几何进入服务层后统一转换为 WGS84，再使用适合当前区域的米制计算方式处理距离、面积和长度。

## 6. 空间关系定义

关系名称必须固定方向，避免 Agent 把 `contains` 的主客体传反。

建议使用面向 Agent 的关系名，底层再映射到几何谓词：

| 关系 | 语义 | 典型数据 |
| --- | --- | --- |
| `at_point` | 找到包含目标点的数据单元 | H3、人口栅格、夜光栅格、POI 栅格 |
| `nearest` | 按真实几何距离返回最近记录 | POI、道路、栅格 |
| `within_distance` | 返回距离目标不超过阈值的记录 | POI、道路 |
| `intersects` | 数据几何与查询几何相交 | 道路、H3、各类栅格 |
| `covered_by` | 数据单元被查询范围覆盖 | H3、人口栅格、夜光栅格 |

不要只返回一个含义不明的 `overlap_ratio`，至少区分：

```text
record_overlap_ratio = 相交面积 / 数据记录几何面积
query_overlap_ratio  = 相交面积 / 查询范围面积
```

人口和夜光的范围聚合还需要返回 `overlap_area_m2`、覆盖方法和统计假设。

## 7. 各类数据的正确算法

### 7.1 POI

POI 是 Point，核心查询是 `nearest` 和 `within_distance`。返回 `distance_m`、`inside_query_area` 和原始 `record_id`。查询层只返回“500 米内有 32 个餐饮 POI”，不直接判断竞争是否激烈。

### 7.2 H3

H3 的核心是空间定位和指标连接，不是普通最近邻：

- 某点属于哪个 H3；
- 哪些 H3 与范围相交；
- 哪些 H3 被范围覆盖；
- 读取 H3 上已有的 POI 指标。

H3 的查询结果必须明确 `h3_id`、分辨率、POI 分析口径和年份。不能返回人口、夜光或路网指标，除非这些指标明确被另一个分析结果关联到该 H3，且来源和方法可追溯。

### 7.3 人口栅格

人口格网的空间查询可以使用覆盖比例做范围估算，但必须明确假设：

```text
estimated_population
= cell_population × record_overlap_ratio
```

返回中应标注：

```json
{
  "method": "area_weighted_sum",
  "assumption": "uniform_distribution_within_cell"
}
```

估算人口不能被写成没有误差的精确普查值。

### 7.4 夜光栅格

夜光通常是强度或均值，不应默认直接求和。更合理的聚合包括：

- 面积加权平均；
- 最大值；
- 分位数；
- 高亮区域面积占比。

每个来源应在 `query_capabilities` 中声明字段适合的聚合方式。

### 7.5 路网线段和路网栅格

路网线段必须使用 Point 到 LineString 的最短距离，不使用道路中心点、起点或终点替代。范围查询还应返回：

- `distance_m`；
- `matched_point`；
- `intersection_length_m`；
- 道路等级和线段 `record_id`。

路网共享栅格是道路指标聚合结果，只能作为 Polygon 栅格查询，不能与路网线段互相替代。步行可达性、连通性和等时圈属于上层网络分析，不由基础空间查询直接计算。

## 8. 返回的空间证据

每条记录除原有 `properties` 外，空间查询应增加 `spatial_match`：

```json
{
  "record_id": "road_edge:r123",
  "spatial_match": {
    "relation": "nearest",
    "distance_m": 34.6,
    "geometry_type": "LineString",
    "matched_point": [112.9802, 28.1898],
    "calculation_crs": "local_metric_crs",
    "distance_unit": "m"
  }
}
```

空间证据必须能回到：

- `source_id`；
- `record_id`；
- 数据年份或版本；
- 原始 locator；
- 实际几何类型；
- 使用的关系和计算方法。

## 9. 查询能力发现

`list_scope_datasets` 不应只返回字段白名单，还要返回每个来源的空间能力：

```json
{
  "source_id": "current:dataset:road_edges",
  "geometry_type": "LineString",
  "coordinate_system": "wgs84",
  "spatial_relations": ["nearest", "within_distance", "intersects"],
  "distance_unit": "m",
  "query_capabilities": {
    "filter_fields": ["road_class", "choice_score"],
    "sort_fields": ["choice_score", "integration_score"]
  }
}
```

Agent 先发现来源和能力，再生成查询。这样不会把道路当成网格，也不会把字段排序误当成临近查询。

## 10. 建议的实现分层

```text
list_scope_datasets
        |
        v
ScopeDatasetService.query_scope_dataset
        |
        v
SpatialQueryEngine
  - 目标几何归一化
  - 记录几何提取
  - 坐标和米制计算
  - contains / nearest / intersects
  - STRtree 空间索引
  - 空间证据输出
        |
        v
POI / H3 / 共享栅格 / 人口 / 夜光 / 路网记录适配器
```

空间计算放在业务域内部，路由层和前端不复制算法。记录查询先执行空间关系，再执行字段过滤、排序和分页；`nearest` 默认按距离排序，其他关系只有在明确指定时才按字段排序。

## 11. 第一阶段范围

第一阶段不建设完整空间分析平台，只完成可靠的空间证据查询闭环：

1. 明确区分 H3、POI 规则栅格、人口栅格、夜光栅格和路网栅格。
2. 支持 Point、GeoJSON geometry 和已有 record 查询目标。
3. 支持 `at_point`、`nearest`、`within_distance`、`intersects`。
4. POI 使用 Point，H3 和各类栅格使用 Polygon，道路线段使用 LineString。
5. 返回 `distance_m`、两个方向覆盖率、相交长度和 `matched_point`。
6. `list_scope_datasets` 暴露真实空间能力、坐标系和年份或版本。
7. 支持按空间结果排序和分页，并保留 `total_count`、`has_more`。
8. 所有记录可通过 `record_id`、`source_id` 和 EvidenceNode 复核。

复杂的人口分配、夜光统计和路网网络分析留在 `aggregate_scope_dataset` 或更高层分析 Skill，不塞进基础记录查询。

## 12. 验收问题

第一阶段完成后，Agent 至少应能准确回答：

- 这个点落在哪个人口、夜光和 POI 栅格？
- 这个点属于哪个 POI H3？
- 距离这个点最近的道路和 POI 是什么？
- 研究范围与哪些 H3、栅格和道路相交？
- 每条记录与目标空间的距离、覆盖率或相交长度是多少？

最终目标可以概括为：

> 构建一个面向 Agent 的多源空间证据查询层，把统一的空间意图按 POI、H3、共享栅格、人口、夜光和路网的几何特征分派到正确算法，并返回可解释、可追溯、可用于后续聚合与分析的空间关系证据。

## 13. 当前实现差距与迁移规则

### 13.1 当前实现差距

第一阶段基线已经落地，当前实现已经覆盖：

- `ScopeDatasetService` 统一读取 POI 与规范化 `analysis_artifacts`，并保留字段过滤、排序、分页、聚合和 EvidenceNode 转换；
- `modules/scope_datasets/spatial.py` 空间查询模块从 Point、Polygon、LineString 和 Multi* 几何计算真实空间关系；
- `query_scope_dataset` 先执行空间关系，再执行属性过滤和分页；`nearest` / `within_distance` 按真实米制距离排序；
- `list_scope_datasets` 返回 `geometry_type`、`grid_type`、输入坐标系、距离单位和支持的空间关系；
- `poi_h3_grid` 与 `poi_raster_grid` 分别映射到 `current:dataset:h3` 和 `current:dataset:poi_grid`；
- 查询记录和 EvidenceNode 均携带 `spatial_match`，包括距离、匹配点、覆盖率、相交面积或道路相交长度；
- Agent adapter 将空间参数校验错误转换为稳定的 domain error，不会静默退回普通字段排序。
- `record` 已作为查询目标接入 Agent 契约，能够以已有 POI、H3、栅格或路段作为另一来源的空间查询目标；
- `aggregate_scope_dataset` 已接受同一套 `spatial`，支持范围计数、人口覆盖比例估算、夜光相交面积加权和道路裁剪长度；
- 新保存的空间 artifact 显式写入 `geometry_coord_type`，缺失时能力发现返回 `spatial_ready=false`，空间查询返回 `spatial_coord_type_unknown`；
- 查询返回 `spatial_diagnostics`，明确匹配数、跳过数和结果是否完整；
- 空间索引缓存键包含记录身份、版本、范围指纹和真实 geometry 摘要，几何变化不会复用旧索引。

当前仍有明确边界：

- 空间索引是进程内缓存，暂不承担跨进程或持久化索引职责。
- 夜光分位数、高值面积占比和道路指标长度加权属于高级分析，尚未加入基础聚合工具；
- `covered_by` 尚未向 Agent 开放，当前使用 `intersects` 返回双向覆盖率；
- 基础查询只证明空间关系和现有字段，不负责步行可达性、网络路径、选址结论或商业判断。

### 13.2 Source 迁移规则

本轮处于 demo 开发期，直接收敛到单一新契约，不保留双字段读取：

| artifact_type | 目标 source_id | 迁移要求 |
| --- | --- | --- |
| `poi_h3_grid` | `current:dataset:h3` | 保留，只允许 POI H3 指标 |
| `poi_raster_grid` | `current:dataset:poi_grid` | 从 H3 映射中移出 |
| `population` | `current:dataset:population` | 声明 `grid_type` 和 Polygon geometry |
| `nightlight` | `current:dataset:nightlight` | 声明 `grid_type` 和 Polygon geometry |
| `road_syntax.road_edges` | `current:dataset:road_edges` | 使用 LineString / MultiLineString |
| `road_syntax.road_grid` | `current:dataset:road_grid` | 使用 Polygon，不与 road edges 合并 |

`current:dataset:h3` 不再兼容读取 `poi_raster_grid`。历史 demo 数据不做双存储兼容；缺少新来源的数据应显示 `pending`，由重新运行分析生成。

### 13.3 几何元数据要求

每个 dataset source 至少声明：

```json
{
  "geometry_type": "Polygon",
  "geometry_coord_type": "gcj02",
  "grid_type": "h3|regular_raster|none",
  "resolution": "source-specific",
  "cell_id_namespace": "poi_h3|poi_grid|population|nightlight|road_grid"
}
```

这里的 `geometry_coord_type` 表示 artifact 原始几何坐标系。进入查询模块后统一转换为 WGS84，因此 `list_scope_datasets.geometry_coord_type` 返回 `wgs84`。不能根据字段名或坐标数值猜测坐标系；artifact 没有明确坐标信息时，能力发现返回 `spatial_ready=false`，空间查询返回诊断错误，不得静默使用默认值计算米制距离。

## 14. 实现拆分

### 14.1 `modules/scope_datasets/service.py`（已完成基线）

负责保持对上层的简单接口，当前已完成：

- 拆分 `poi_h3_grid` 与 `poi_raster_grid` 的 source 映射；
- 在 `list_scope_datasets` 中返回空间能力；
- 在 `query_scope_dataset` 中编排年份选择、空间查询、属性过滤、排序和分页；
- 将 `spatial_match` 写入记录和 EvidenceNode；
- 保持存储细节不进入 Agent 工具契约。

### 14.2 `modules/scope_datasets/spatial.py`（已完成基线）

该深模块已负责：

- 校验并归一化 Point / GeoJSON 查询目标；
- 从 POI、H3、各类栅格和路网记录提取真实几何；
- GCJ-02 与 WGS84 转换；
- 构建适用于当前范围的米制计算环境；
- 使用 Shapely `STRtree` 做候选检索；
- 计算 `at_point`、`nearest`、`within_distance`、`intersects`；
- 输出距离、最近投影点、相交面积、覆盖率和相交长度；
- 按 `history_id + source_id + year + data_version + scope_fingerprint + geometry digest` 缓存空间索引。

路由层、Agent adapter 和前端不得复制这些算法。

### 14.3 Agent 工具契约（已完成基线）

`modules/agent/tool_definitions/scope_datasets.py` 已完成：

- 在 source enum 中加入 `current:dataset:poi_grid`；
- 为 `query_scope_dataset` 增加严格的 `spatial` schema；
- 支持 Point、GeoJSON geometry 和已有 `record` 三种目标；
- 在输出记录中增加可选 `spatial_match`；
- 在查询输出中增加 `spatial_diagnostics`；
- 更新工具描述和 cautions，要求临近问题使用空间关系；
- 明确 `max_distance_m` 的单位、范围和缺省行为。

`modules/agent/tool_adapters/scope_dataset_tools.py` 只透传已校验参数和结构化结果，不重建空间规则。

### 14.4 空间聚合（已完成基础闭环）

`aggregate_scope_dataset` 已接受同一 `spatial`，当前支持：

- POI：范围计数、分类计数；
- 人口：`area_weighted_sum`，按 `record_overlap_ratio` 估算并声明单元内均匀分布假设；
- 夜光：`area_weighted_avg`，按 `overlap_area_m2` 计算面积加权均值；
- 道路：`intersection_length_sum`，汇总裁剪后的相交长度；
- H3 / POI 栅格：相关单元计数和已有 POI 指标聚合。

聚合结果返回 `metric_methods`、`assumptions`、`matched_record_count`、空间范围摘要和可引用 EvidenceNode。人口相交范围使用普通 `sum`、夜光相交范围使用普通 `sum/avg` 会被拒绝，避免整格误算。夜光分位数、高值面积占比和道路指标长度加权保留为后续高级分析能力。

## 15. 错误与诊断契约

空间查询不能在失败时退回普通字段排序，否则 Agent 会把错误结果当作真实临近结果。建议稳定返回以下 domain error：

| error | 含义 |
| --- | --- |
| `spatial_query_invalid` | relation、目标几何或参数不合法 |
| `spatial_relation_unsupported` | 当前来源不支持请求的关系 |
| `spatial_geometry_missing` | 数据记录没有可用几何 |
| `spatial_coord_type_unknown` | 无法确认输入或数据几何坐标系 |
| `spatial_metric_calculation_failed` | 距离、面积或长度计算失败 |
| `spatial_target_record_not_found` | record 查询目标不存在 |
| `scope_dataset_field_unsupported` | 使用了来源未声明的过滤、排序、分组或聚合字段 |
| `spatial_aggregate_invalid` | 空间聚合缺少 `intersects` 目标 |
| `spatial_aggregate_unsafe` | 请求了会导致整格误算的聚合方法 |

单条坏记录可以跳过，但结果必须返回：

- `skipped_record_count`；
- 按原因分组的 warnings；
- 是否影响结果完整性的标志。

当全部记录都缺少几何时，工具返回失败，不返回空成功结果。

## 16. 测试计划

### 16.1 来源边界

- `poi_h3_grid` 只出现在 `current:dataset:h3`；
- `poi_raster_grid` 只出现在 `current:dataset:poi_grid`；
- 人口、夜光、路网栅格不能通过 H3 source 查询；
- `list_scope_datasets` 正确返回各来源的 geometry、grid type 和关系能力。

### 16.2 空间正确性

- GCJ-02 查询点能够命中转换后的 WGS84 数据几何；
- 边界上的点使用覆盖语义稳定命中所属 Polygon；
- 道路 nearest 使用点到线的最近距离，不使用中心点、起点或终点；
- `within_distance` 严格执行米制阈值；
- Polygon 相交返回两个方向的覆盖率；
- 道路与范围相交返回裁剪后的 `intersection_length_m`；
- MultiPolygon 和 MultiLineString 能正确处理；
- 无效 geometry、未知坐标系和缺失 geometry 返回明确诊断。

### 16.3 查询组合

- 空间关系与属性 filters 同时生效；
- `nearest` 在属性过滤后对合法候选按距离排序；
- 非 nearest 查询遵循显式 sort；
- 空间筛选后的 `total_count`、`offset`、`limit`、`has_more` 正确；
- `spatial_match` 同时进入 records 和对应 EvidenceNode；
- record 目标能够跨来源查询，并在同源查询中默认排除自身；
- `spatial_diagnostics` 返回跳过数和完整性状态；
- `read_scope_record` 仍能通过返回的 `record_id` 复核原始记录。

### 16.4 性能与缓存

- 典型当前范围 POI、道路和栅格规模下不做全量两两几何比较；
- 同一数据版本重复查询复用 STRtree；
- history、year、data version 或 scope fingerprint 变化时索引失效；
- 缓存不改变排序、距离和覆盖率结果。
- 相同记录 ID 的 geometry 变化时缓存键变化；
- 中纬度东西方向的半径候选不会因经纬度比例不同而漏查。

### 16.5 空间聚合与 Agent

- 人口半格覆盖按覆盖比例估算，不按整格求和；
- 夜光不同覆盖面积按相交面积加权；
- 道路只累计查询范围内裁剪后的长度；
- 不安全的空间聚合返回稳定错误；
- 聚合方法、假设和空间摘要进入可引用 EvidenceNode；
- `list_scope_datasets` 暴露每个来源的 `spatial_ready` 和可用空间聚合方法。

## 17. 完成定义

第一阶段只有同时满足以下条件才算完成：

1. H3 与 POI 规则栅格在 source、artifact 映射、查询能力和测试中完全分离。
2. POI、H3、POI 栅格、人口、夜光、路网线段和路网栅格都有明确 geometry adapter。
3. 四个第一阶段空间关系通过真实几何测试。
4. 所有米制结果携带计算方法、单位和可复核空间证据。
5. Agent 能通过能力发现选择正确 relation，并得到可引用 EvidenceNode。
6. 空间错误不会静默退化为字段排序或空成功结果。
7. 现有字段查询、聚合、分页和单条读取契约没有回归。
8. 相关 domain、Agent tool、API 和前端工具详情测试全部通过。

本文同时记录实现边界和验收口径。当前代码已完成第一阶段记录查询、record 目标、显式坐标契约、查询完整性诊断、基础空间聚合和 Agent EvidenceNode 闭环；后续高级分析能力仍必须沿用本文的来源边界和证据规则。
