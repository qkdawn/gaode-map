# 工程演进与方法决策记录

最后核对日期：2026-08-18

## 1. 记录目的

本文记录“基于等时圈与多源空间数据的多智能体区域分析报告生成方法”从固定十二步原型演进到动态决策研究链路的过程。它服务于三个用途：解释当前架构为何如此设计；为后续复现实验保留可核对的工程条件；为论文的方法、消融和局限章节提供素材。

本文不是效果证明。所有记录按以下证据等级使用：

| 等级 | 含义 | 论文中的用途 |
| --- | --- | --- |
| 架构事实 | 已由当前源码、契约或测试确认 | 描述方法实现 |
| 运行事实 | 可由运行 ID、数据库状态或产物确认 | 描述可行性或故障 |
| 工程判断 | 根据故障和设计权衡作出的选择 | 提出设计假设和消融变量 |
| 待验证假设 | 尚未完成匹配基线、重复运行或专家评价 | 只能写成研究问题或假设 |

VPN 路由、模型中转站异常、单次超时和一次成功或失败运行都只能算运行条件，不能直接证明某种多智能体方法更好或更差。

## 2. 当前参考实现

当前源码生成的 N8N 工作流有 95 个节点。节点数只是实现规模，不是研究贡献。方法链路为：

```text
项目问题与项目上下文
→ 规划 Agent 生成动态 decision_units
→ 证据路由 Agent 为当前单元选择 1–3 个独立工具请求
→ N8N 串并行执行取证并形成有界工作简报
→ 研究分析 Agent 生成 decision_memo
→ 跨单元综合 Agent 生成 report_blueprint
→ 统一写作 Agent 按蓝图逐节成稿
→ 受限全局编辑、图件生成、报告装配与投递
```

四类证据源保持独立：

| 证据源 | 模型侧入口 | 当前边界 |
| --- | --- | --- |
| 空间数据库 | `analyze_spatial_evidence` | POI、人口、路网、夜光、H3；内部完成空间计算，只返回受限事实 |
| 文献知识库 | `search_literature_evidence` | GraphRAG 的 `focused` 原文检索与 `synthesis` 跨文档综合 |
| 项目文档 | `read_project_document` | Docling 解析后分页读取原文 |
| 实时互联网 | `search_public_web`、`fetch_public_web_page` | 搜索用于发现，网页全文才可进入证据上下文 |

计划、研究、综合和写作 Agent 不直接调用工具。证据路由 Agent 只决定取证，不负责形成项目结论；工具只返回事实，不在代码中决定下一步研究策略。

## 3. 问题、根因与改造结果

### 3.1 固定十二章导致研究结构先于项目问题

**原表现**：十二个常见方向被固化为十二个执行步骤和十二章。即使项目只需要少数核心判断，也会机械覆盖政策、市场、客群、产品、空间、运营、财务和分期。

**问题**：章节数量与真实决策问题脱节；不同章节容易重复使用同一批空间事实；工作流复杂度随模板增长。

**选择**：十二个方向只保留为规划 Agent 的启发，不再作为运行模板。规划 Agent 输出数量不固定的 `decision_units`，每个单元必须声明 `decision_output` 和 `depends_on`。32 个单元只是异常保护上限，不是默认数量。

**论文含义**：动态决策分解可以作为与固定十二步基线比较的独立变量。当前只能说明契约已经实现，不能说明它必然提高分析深度。

### 3.2 决策单元过少或过粗

**原表现**：新版真实运行只规划出三个单元：功能结构、机会类型和空间落点。逻辑顺序成立，但中间机制可能被合并得过粗。

**根因判断**：问题不在代码固定为三个，而在规划 Agent 对“什么算一个会改变后续选择的新判断”理解过于概括；同时旧提示词容易把常见十二方向误解为应压缩的目录，而不是可展开的思考视角。

**选择**：数量继续由 AI 根据项目决定，不设业务默认值。通过 `decision_output` 的独占性、依赖关系和规划前自检引导必要拆分；工作流只校验结构和上限，不在代码中判断项目应有几个单元。

**待验证**：需要比较不同规划提示和案例下的单元数量、有效问题覆盖率与重复率，避免把“单元更多”误当成“分析更深”。

### 3.3 同一空间结论在多章反复出现

**原表现**：旧报告反复使用 231 个网格、2 个共同高值和 51.1% 冲突，连续得出“多节点、弱廊道、连接器”等近似结论。章节顺序存在，但论证没有推进。

**根因**：每章单独取证并直接成稿，没有一个跨单元结构明确“本单元新增什么、哪些前序结论只可引用而不得再次证明”。

**选择**：单元阶段只生成结构化 `decision_memo`；完成全部单元后，由综合 Agent 生成 `report_blueprint`。蓝图声明每节的新结论、来源单元、必须保留的数字和具名对象、可引用但不得重复证明的前序结论。写作后只允许受限删除、标题和格式等价术语调整，避免全局重写丢失证据。

**论文含义**：递进性和重复率应成为报告评价指标，而不是只比较篇幅或章节数。

### 3.4 空间证据不够具名

**原表现**：报告能描述密度、方向和网格关系，却不能回答“连接哪一家设施、沿哪条道路、形成什么互补”。

**根因**：原空间响应偏重聚合结果；POI 名称、类别、地址、道路名称和道路等级没有稳定进入模型工作上下文，结果压缩还可能进一步丢失具名对象。

**选择**：`analyze_spatial_evidence` 保留七种通用语义：`scope`、`accessibility`、`direction`、`neighborhood`、`rank`、`relationship` 和 `inspect`。其中 `inspect` 可展开具名 POI、相交道路和邻近对象。工作简报单独保留最多二十条具名空间记录，`decision_memo.named_entities` 和蓝图 `must_include_named_entities` 继续把关键名称传给写作 Agent。

**边界**：名称存在不等于设施真实运营、道路适合改造或关系具有因果性。具名化提高可核对性与项目可读性，但其质量仍需抽样核验。

### 3.5 深接口与上下文膨胀之间的矛盾

**原表现**：如果把所有空间字段、文档全文和每次 `function_call_output` 持续带回模型，上下文会迅速膨胀，并曾出现代理窗口内无法完成、Cloudflare 524 或 `context_budget` 风险。反过来，若只保留极短摘要，又可能丢失 POI、道路和决定性数字。

**选择**：深接口隐藏表名、字段名、几何和计算细节，但单次结果仍受上限控制。完整工具结果在当前执行的临时结果存储中保留；回到模型的是 `working_research_brief`、最近结果和具名空间记录。空间结果约束组数、高亮数和字符预算，文档通过 Docling 分页，旧 `function_call_output` 不无限累积。

**保真机制**：关键数字进入 `key_facts`，具名对象进入 `named_entities`，蓝图从来源备忘录确定性提取强制事实和名称。这样压缩的是重复正文和内部数据结构，不应压缩会改变判断的项目事实。

**清理策略**：成功运行只持久化研究框架、决策单元、`decision_memo`、最小来源元数据、蓝图、报告节和最终产物。完整工具正文不进入长期 `decision_state`。N8N 配置为成功执行不保存完整执行数据，失败执行保留并在 168 小时后清理。

### 3.6 “下一步查什么”被写进空间工具

**原表现**：曾考虑让空间工具返回 `expansion.required` 和 `next_request`。

**否决原因**：这会把研究策略硬编码进数据层，使空间工具同时承担事实计算和研究规划，且难以适应不同项目问题。

**选择**：空间工具只返回事实、覆盖率和限制。独立的低成本证据路由 Agent 根据当前单元、依赖备忘录、已有事实和预算决定是否展开、下一步调用什么或结束。代码只做参数、权限、重复、预算和并行边界校验。

### 3.7 每轮单工具造成等待和无效串行

**原表现**：项目文档、空间查询和文献检索彼此独立时仍逐个执行，单元耗时近似各调用耗时之和。

**选择**：路由 Agent 每轮返回 1–3 个参数已经完整且相互独立的请求，N8N 将同批 item 并行执行，并按 `batch_index` 恢复确定性顺序。只有参数依赖上一结果时跨轮串行，例如网页搜索后抓正文、当前文档页后读下一页、取得 `record_ref` 后执行 `inspect`。

**故障语义**：同批部分失败时保留成功结果；整批全部失败才累计连续失败批次。总工具预算按实际请求数计算，不按批次数计算。并行限制只影响取证，不限制研究和写作推理。

### 3.8 文献库和实时互联网被错误视为一个入口

**原表现**：旧链路在每章前自动检索公共知识库，并曾强制首次联网或要求双通道证据。

**问题**：本地 PDF 文献解决规范、方法和跨案例机制，互联网解决最新政策、机构和当地公开事实；合并会模糊时效性、隐私和引用边界，也会产生与当前问题无关的固定成本。

**选择**：二者永久保持独立。`search_literature_evidence` 是唯一文献入口，`focused` 直接查 GraphRAG 索引原文，`synthesis` 才调用跨文档综合；互联网继续使用搜索与全文读取两步。取消每章前置 GraphRAG、强制联网和强制双通道。

**当前语料事实**：`source_manifest.json` 登记 18 份 PDF。2026-08-18 运行索引覆盖校验得到 18 个文档、265 个文本单元、9,177 个实体、11,939 条关系、504 个社区和 504 份社区报告，未发现缺失文档或无文本单元文档。该结果证明索引覆盖，不证明检索答案正确。

**当前模型分工**：GraphRAG 建图与综合使用当前配置的 `gpt-5.6-sol`；向量由 11435 上的本地 `jinaai/jina-embeddings-v2-base-zh` 生成。N8N 证据路由使用 `gpt-5.6-terra` 是另一项运行选择，不能把两个模型配置混写成同一实验条件。

### 3.9 项目文档只给目录，模型实际没有读正文

**原表现**：工作流把文档目录交给 Agent，但 Agent 可能不调用读取工具，最终报告看起来像没有看过项目材料。另一问题是固定“最多二十块”无法表达文档是否已经读完。

**选择**：统一使用 Docling 解析项目文档；`read_project_document` 返回正文块、`complete`、`next_start_block` 和总块数，可按需多次分页。当前动态路由版本不再把“每章必须预读一份文档”写死，而是把文档目录与当前决策问题交给路由 Agent，由它在项目事实确实相关时选择首段和后续分页。

**边界**：文档标题和页码主要用于识别内容与继续分页，不要求生成形式化引用列表；正文是否被实际读取应由工具调用记录和备忘录内容共同核对。

### 3.10 原始空间接口泄漏数据实现

**原表现**：旧模型侧工具 `project_context` 和 `query_data` 暴露过多数据契约、范围和字段细节，并且 H3、POI 规则栅格与路网共享栅格的能力不一致。

**选择**：模型侧只公开 `analyze_spatial_evidence`。`history_id` 由 N8N 注入，模型不能提交数据库标识、任意 Polygon、坐标系或原始字段名。空间服务内部根据点、面状栅格、H3 和路网策略完成包含、距离、面积加权、相交长度与共享分析单元对齐。模型响应递归剔除几何、坐标数组、数据库连接和本地文件路径。

**论文含义**：深接口的研究价值应通过工具调用正确率、空间数值一致率和上下文成本检验，而非只凭“接口更少”判断。

### 3.11 嵌入服务与 GraphRAG 代理层

**原表现**：项目本地嵌入服务最初使用 Ollama 风格 `POST /api/embed`，GraphRAG 需要 OpenAI-compatible `POST /v1/embeddings`，因此临时增加 11436 格式转换代理。

**否决原因**：单纯格式转换的代理没有独立业务语义，增加一个端口、进程和故障点。

**选择**：让 11435 的本地 Jina 嵌入服务直接实现 `/v1/embeddings`，删除 11436。建库时由本地嵌入模型把 PDF 文本单元转换为向量；完成模型负责 GraphRAG 的实体、关系和综合，不负责生成向量。

**论文边界**：索引是可重建派生物，原始 PDF 才是事实源；后续应记录嵌入模型版本并进行跨语言召回评估。

### 3.12 过度兼容和回退掩盖真实契约

**原表现**：早期实现保留旧工具名、旧字段、目录回退、旧 GraphRAG HTTP 端点和恢复性成稿分支，测试“回退路径通过”容易被误解为产品能力。

**选择**：demo 阶段直接收敛到单一契约。删除模型侧 `project_context/query_data`、旧 `read_previous_chapter`、旧 GraphRAG HTTP/N8N 入口和无人消费的兼容分支；调用方、测试和文档同步升级。只有运行恢复所需且能改变处理结果的故障状态才保留。

### 3.13 缺失数据提示反客为主

**原表现**：报告不断要求补充建筑面积、权属、消防、客流、付费意愿和运营承诺，即使用户明确要求只根据现有 POI、人口、路网、夜光与 H3 分析。

**选择**：工具仍如实返回覆盖和限制，但研究与写作提示删除与当前结论无关的反向补数清单。未知只降低结论强度，不自动阻塞当前尺度能够支持的判断；不能由现有数据回答的财务、真实客流或经营问题不应主动展开。

**论文边界**：这是一项写作范围控制，不应被解释为消除不确定性。评价时仍要检查模型是否把代理变量写成真实需求或因果事实。

### 3.14 财务、运营和分期计算暂不进入当前工具集

**曾考虑路线**：对模型只暴露一个 `evaluate_decision_scenario` 深接口，内部调用运营、财务和分期模块，避免暴露大量浅层公式。

**当前问题**：可靠计算至少需要产品或空间容量、开放时段、人员配置、单价或公共价值交换、客流或使用频率、建设与运营成本、资金上限、责任主体和分期前置条件。当前项目起始阶段通常只有 POI、人口、路网、夜光、H3 和部分项目文档，缺少上述项目级输入。

**选择**：当前四类证据工具不包含财务场景计算器，也不使用行业默认值补齐缺失数据。规划 Agent 可在材料确实提供这些输入时生成相关决策单元；未来若实现该工具，输入不足必须返回 `not_calculable`，不能输出伪精确收益、现金流或分期门槛。

**论文含义**：当前方法研究的是等时圈内多源空间证据如何支持区域判断，不把投资级财务可行性作为已实现能力。

### 3.15 生产 Webhook 返回 404

**原表现**：工作流已经导入并标记 active，但生产 Webhook 直接 POST 返回 404，容易被误判为业务节点或请求 payload 错误。

**根因**：当前 N8N 2.x 导入 active workflow 后没有可靠重建 `webhook_entity` 注册记录；编辑器中的工作流状态与生产 Webhook 注册状态不是同一事实。

**选择**：bootstrap 在导入后从 workflow 的 Webhook 节点确定性同步 `webhook_entity`，再做 smoke test。该处理属于部署边界，不在业务路由中增加 404 fallback，也不把测试 Webhook 当生产入口。

**论文边界**：Webhook 注册故障只能说明参考实现的部署要求，不能作为 Agent 方法优劣证据。

### 3.16 运行目录、Git 与 worktree

**原表现**：`runtime/`、`tmp/`、`.codex-tmp/` 和 `.vs/` 中包含索引、报告、分析结果和编辑器产物；直接在脏工作区创建 worktree 或清空目录会制造 Git 噪声，也可能误删仍需用于复现的报告。

**选择**：在 `.gitignore` 中忽略这些运行目录，再使用 worktree 隔离代码任务；不以递归删除作为清理手段。运行产物由其所属服务的保留策略管理，需要进入论文证据链的结果通过稳定 run ID 和来源清单登记，而不是把整个 `runtime/` 提交到 Git。

**论文含义**：Git 只保存可重建实现与最小清单，原始数据和运行产物使用独立事实源；复现清单必须说明如何从事实源重建派生索引与报告。

### 3.17 直线距离分带与等时圈语义冲突

**原表现**：七种空间分析中的旧 `distance` 模式虽然只分析保存等时圈内的单元，却按项目中心到单元中心的平面直线距离分为 0–500、500–1000 和 1000–1600 米。该分带没有使用路网，也不是等时圈的旅行时间成本。

**问题**：同一接口同时声称“以等时圈为共同范围”又用欧氏距离表达内部梯度，模型容易把几何邻近误写成步行可达性。道路绕行、断点和网络连接差异会被隐藏。

**选择**：删除模型侧 `distance` 和 `distance_bands_m`，不保留兼容入口；新增 `accessibility` 和 `travel_time_bands_min`。分析范围仍固定为当前保存等时圈，内部使用同一项目锚点、出行方式和 Valhalla 成本模型生成嵌套 contour。当前 15 分钟项目默认一次请求 5、10、15 分钟等时圈；其他阈值默认等分为三段。空间单元按代表点落入的最小 contour 归类。Valhalla 失败或 contour 不完整时返回 `unavailable`，不使用适配器原有的圆形 buffer，也不以直线距离补值。

**输出边界**：方位分析和地图识别仍可返回 `straight_line_distance_m`；可达性分带另行返回 `travel_time_band_min`、`travel_time_upper_bound_min` 和 `travel_time_source=valhalla_isochrone_contour`。嵌套 contour 只证明单元落在某个时间区间，不能写成该单元具有某个精确导航时间，更不能写成实测步行时间。

**论文含义**：后续实验应比较直线距离分带与网络时间分带对空间归类、具名节点排序和专家判断的影响，并把路网覆盖率与不可达单元比例纳入结果。

## 7. 可进入论文的方法论观察

以下内容可以转化为论文假设或实验变量，但尚不能写成已经证实的优势：

1. 动态决策单元可能比固定章节更适合不同项目，但需比较有效问题覆盖、重复率和专家评价。
2. 深空间接口可能降低字段误用和几何泄漏，但需比较工具调用正确率、数值一致率、上下文成本和可解释性。
3. 证据路由与研究推理解耦可能降低工具格式对分析表达的干扰，但需与单 Agent 原生函数调用对照。
4. 有界简报、具名记录和结构化备忘录可能在控制上下文的同时保留关键事实，应测量关键数字和名称的召回率。
5. 跨单元蓝图可能降低重复并改善递进，应测量重复事实比例、结论依赖正确率和段落新信息率。
6. 受控串并行可能降低取证等待时间，但需报告同批失败率、端到端时延、调用成本和结果确定性。
7. `focused` 文献原文检索与 `synthesis` 综合分离可能改善证据边界，应分别评价跨语言召回、原文覆盖与综合答案可核验性。
