# N8N 与多智能体工具体系批判性审查（历史版本）

> 本文记录旧 `project_context/query_data/read_previous_chapter` 契约下的审查过程，不再代表当前实现，也不能作为开发规范。当前动态决策单元、证据路由 Agent、四类证据工具、`decision_memo` 和动态报告蓝图以《N8N 动态决策研究与证据工具执行方式》为准。

## 1. 审查结论

当前系统已经具备一条“取证—写作—装配报告”的可运行链路，但还不是一套完整的等时圈区域决策分析工具。它最擅长回答：

- 当前项目有哪些文档、数据集和已计算结果；
- 等时圈或其他空间范围内有哪些 POI、人口、夜光、H3 和路网记录；
- 某个阶段如何基于已有证据生成章节、引用和诊断；
- 如何把章节、图件和引用装配成 Markdown、Word 或飞书交付物。

它还不能稳定回答：

- 所有数字是否确实来自同一个等时圈、同一数据快照和同一统计口径；
- 两个或多个候选定位、产品或空间方案相比，为什么选择其中一个；
- 一个产品组合的容量、成本、收入、运营责任和分期条件是否闭合；
- 这次报告能否仅凭保存的数据稳定重放，而不是只能看到最后引用了哪些证据。

因此，当前系统应被表述为“共享空间证据工具箱上的自适应多阶段报告生成工作流”，不宜表述为“十二个专业 Agent 已分别完成完整分析”，也不宜把工具数量本身当作方法贡献。

## 2. 当前工具面的实际构成

### 2.1 N8N 主工作流直接使用的工具

N8N 章节循环目前向同一个 spatial-project MCP 暴露六个工具：

| 工具 | 当前能力 | 判断 |
|---|---|---|
| `project_context` | 返回项目、文档、空间范围、数据集和已计算结果的目录与摘要 | 保留；是项目入口，但职责较宽 |
| `query_data` | 按数据集读取记录或做聚合，可选空间过滤、分页和快照续查 | 保留并升级；目前没有强制绑定等时圈 |
| `read_project_document` | 按文档、文本块和页码读取项目原文 | 保留；需要更强的冲突和版本输出 |
| `read_previous_chapter` | 读取已完成前序章节和阶段性结论；由调用方传入已完成章节目录，MCP 校验阶段边界 | 保留；需要纳入硬性决策约束 |
| `search_public_web` | 通过 AnySearch/Exa 发现公开网页 | 保留；返回结构和来源质量需要升级 |
| `fetch_public_web_page` | 抓取候选网页全文，失败页面进入诊断 | 保留；应和通用 Agent 工具注册统一 |

主工作流还自动执行本地公共知识库混合检索，并在章节结束后生成图件、总判断和报告。默认十二阶段是回退计划；运行时研究框架可生成 1 至 32 个方向，所以当前实现不是固定十二个专业 Agent 的并行编制。

### 2.2 通用 Agent 工具注册面

`modules/agent/tools.py` 当前注册 18 个工具，主要包括：项目上下文、当前范围、当前结果、POI 查询、分析/报告/已选来源检索、范围数据集列表/查询/聚合/单条读取、商业分析计划和公开网页搜索。

这里存在一个重要契约不一致：通用注册面有 `search_public_web`，但没有 `fetch_public_web_page`；而 N8N 的 MCP 面已经有搜索和全文抓取两个工具。也就是说，“知识库 + 互联网全文”在 N8N 主流程中成立，在其他 Agent 入口中并不成立。

状态含义：**满足**表示当前链路可直接支持；**部分满足**表示已有组件，但不能保证结论成立；**未满足**表示缺少决定性工具或质量门。

|---|---|---|---|---|

| 从数据形成“数值—比较—取舍” | 部分满足 | 有聚合、证据节点、报告验证器和部分比较基准检查 | 没有统一的候选方案、基准、权重、反例和裁决结构；质量门只检查证据数量和来源状态，不检查是否完成比较与选择 | **P0** |
| 供给、客群和区域机会判断 | 部分满足 | POI 聚合、人口代理、商业分析计划、Huff 等模型图设计存在 | `plan_business_analyst_analysis` 主要生成分析骨架，不是完整计算；缺少真实客流、消费、租金和经营校准时，报告仍可能把代理指标写成机会 | P1 |

| 失败、缺失和不确定性诊断 | 部分满足 | 有工具错误、网页不可用、缺失来源、代理指标边界和降级状态 | 缺少按阶段的最低数据覆盖门；可能出现有引用但关键数据集缺失、年份冲突或空间范围不一致的“形式通过” | P1 |
| 工具调用可复核和可重放 | 部分满足 | 后端运行时有延迟和调用 trace 结构；N8N 保存证据、诊断和阶段状态 | N8N 持久化结果没有完整保存每次工具的名称、参数、耗时、返回状态和结果指纹，不能稳定重放本次研究过程 | **P0** |
| 图件和报告交付 | 满足 | 后端确定性绘图、Markdown/Word 装配、引用和飞书交付已形成 | 图件设计依赖模型选择；尚缺“图件是否改变决策”的统一验收字段 | P2 |
| 数据安全和公网边界 | 满足 | AnySearch 密钥留在后端；提示词限制不得发送未公开项目信息 | 还需要在工具层而非只在提示词层做敏感字段拦截和查询审计 | P1 |

## 4. 必须更新的工具

### P0：先修复会导致事实错误或无法复核的问题

1. **升级 `query_data` 为范围绑定查询**

   默认从 `history_id` 解析唯一的 `scope_id`、等时圈几何、出行方式、时间阈值、入口、路网版本和数据快照。查询结果必须返回 `scope_id`、`scope_checksum`、`spatial_relation`、`overlap_rule`、`selected_year` 和 `complete`。没有明确的比较模式时，拒绝无空间条件的全库查询。这样才能证明“等时圈内”不是一段提示词，而是工具契约。

2. **新增确定性的 `run_isochrone_analysis`，或把它合并进现有空间分析入口**

   输入应包括起点/入口、出行方式、时间阈值、路网版本和服务版本；输出应包括几何、参数、失败原因、覆盖诊断和可比较的 `scope_id`。支持一次请求比较多个时间阈值或入口，避免模型凭文字比较不同范围。不要只新增一个转发 Valhalla 的浅包装，工具应同时负责快照、版本和结果登记。

3. **新增跨源比较/候选裁决工具**

   `aggregate_scope_dataset` 能在一个数据源内聚合，但不能稳定完成“同一 H3/同一等时圈内，POI—人口—夜光—路网”的对齐。应增加一个深模块，例如 `build_spatial_evidence_matrix`，输入统一范围、分组单元、指标和基准，输出数值、比较基准、时间口径、缺失项和不能证明的内容。对定位、产品、入口或候选分区，再增加同一接口的 `alternatives` 输入，输出排序依据、反例和未决条件。

4. **统一互联网工具契约**

   在通用 Agent 注册面补上 `fetch_public_web_page`，并让 N8N 与通用 Agent 共用同一适配器。`search_public_web` 返回结构化候选（URL、标题、摘要、域名、发布主体、日期、检索时间和 provider），全文工具返回每个 URL 的成功状态、正文、发布日期、页面主体、抽取限制和引用 ID。搜索摘要永远只能是发现线索，质量门应检查“已抓取正文 + 来源主体 + 日期”，而不是仅检查搜索是否调用。

5. **把质量门从“证据数量门”升级成“决策闭合门”**

   每章至少登记：目标决策、候选路径、采用的比较基准、支持证据、反证、硬约束、缺失证据、不能证明的结论、下一阶段必须遵守的约束。`evidence_count > 0` 不能再等价于 `grounded`。没有等时圈绑定、关键年份、比较基准或候选取舍时，应返回 `evidence_gap` 或 `decision_open`。

6. **持久化 N8N `tool_trace`**

   每次调用至少保存 `trace_id`、阶段、模型轮次、工具名、脱敏参数、开始/结束时间、耗时、状态、错误、结果指纹、证据 ID 和快照 ID。正文仍只展示引用，但审计和论文实验可通过 trace 重放工具链。参数需在写库前做敏感字段脱敏。

7. **增加确定性运营/财务/分期校验器**

   不要让语言模型单独承担“可行性”。新增一个受约束的场景工具，输入容量、开放时段、人员、成本、价格/价值交换、收入或公共服务目标、资金上限和分期前置条件；输出区间、敏感变量、缺口和停止条件。缺少输入时返回 `not_calculable`，不得用默认值补齐。

### P1：修复决策链断裂和工具面混乱

1. **把 `read_previous_chapter` 的自由文本升级为结构化阶段记忆**：至少分开 `must_do`、`must_not_do`、`assumptions`、`open_questions`、`reversal_conditions`，后续阶段保存“已消费的约束”和冲突说明。
2. **把夜间判断做成显式条件分支**：出现夜间产品、晚间运营或夜光证据时强制执行 `nightlife_baseline`；产品和空间草案形成后强制执行一次 `nightlife_product_check`，并将结果作为布局和运营阶段的输入。
3. **统一项目数据接口的命名和来源**：N8N 的 `project_context/query_data/read_project_document` 与通用 Agent 的 `read_project_context/list_scope_datasets/query_scope_dataset` 目前是两套词汇和两套返回契约，应收敛到同一底层 schema。
4. **更新 `plan_business_analyst_analysis` 的名称和边界**：它目前更接近“生成商业分析骨架”，不是完成商业分析。应改名为 `build_business_analysis_plan`，输出明确的待计算模型、所需输入和不可计算原因；完整结果只能来自确定性模型工具。
5. **让 `/project-data/step` 二选一**：要么接入主工作流，作为每章的确定性预取和证据包；要么标记废弃并删除 `_STEP_DATASETS` 及相关路由、测试，避免同时维护“阶段预取”和“模型自主查询”两条互相不一致的路径。

## 5. 应从模型可见工具箱删除或合并的入口

这里的“删除”指从 Agent 的主要工具面撤下，不等于立即删除所有后端代码。先做观测期和调用统计，再删除兼容入口。

| 入口 | 建议 | 原因 |
|---|---|---|
| `query_current_pois` | 从主 Agent 工具面撤下，与 `query_scope_dataset(source_id=poi)` 合并 | 两者都读当前范围 POI；并存会让模型在分页、年份、空间关系和引用契约之间做无意义选择。前端专用查询可暂留内部适配器 |
| `read_current_scope` 与 `project_context` 的范围部分 | 合并为一个规范的 `read_scope` 结果；保留快速读取别名但不暴露给模型 | 当前一个读 analysis snapshot，一个读 history project，容易造成范围和版本来源混淆 |
| `read_current_results` 与 `search_analysis_context` | 不直接删除；把前者降为缓存/摘要内部能力，模型统一通过 `search_analysis_context` + `read_analysis_evidence_node` 取证 | 避免“摘要结果”和“证据节点”两套引用方式 |
| `search_report_context` 与核心研究工具 | 保留，但只在报告追问场景开放 | 它服务复盘，不应污染前置研究阶段的工具选择 |
| `list_selected_sources`、`search_selected_source_evidence`、`read_selected_source_evidence_node` | 合并为带 `source_scope` 的通用证据检索；旧接口进入兼容期 | 当前“已选来源”“分析上下文”“报告上下文”分成多套检索词汇，增加模型记忆负担 |
| `/project-data/step` | 若不接入 N8N，则废弃 | 现有实现有测试和路由，但主工作流不使用；保留会让文档暗示每阶段已按映射取数 |
| 旧的阶段/目录兼容别名 | 在 demo 阶段删除 | 项目约束已明确不为历史 payload 和旧字段保留无意义兼容层 |

不建议删除 `project_context`、`query_data`、`read_project_document`、`read_previous_chapter`、`search_public_web` 或 `fetch_public_web_page`。它们分别承担项目入口、空间证据、原文证据、跨章记忆和外部公开证据，删除只会把复杂度推回模型提示词。

## 6. 建议收敛后的最小核心工具面

面向 N8N 主工作流，建议最终只让模型看到以下九类深工具：

1. `read_project_context`：项目、文档、数据集、范围和版本目录。
2. `read_scope`：规范化等时圈、入口、方式、阈值和快照。
3. `run_isochrone_analysis`：计算或比较等时圈。
4. `query_scope_evidence`：统一记录、聚合和跨源证据矩阵查询。
5. `read_project_document`：按原文位置读取项目材料。
6. `search_public_web`：结构化发现公开来源。
7. `fetch_public_web_page`：取得可引用网页全文。
8. `read_previous_decision`：读取结构化上游约束和完整章节。
9. `evaluate_decision_scenario`：候选、产品、运营、财务和分期的确定性校验。

图件设计、报告装配、Word/飞书交付继续由工作流节点和后端服务完成，不必全部暴露为章节 Agent 工具。通用 Agent 的报告追问可以在另一个受限工具面中打开报告检索工具。

## 7. 实施顺序和验收标准

### P0 实施顺序

1. 统一 `scope_id`、快照和空间查询契约，补等时圈计算/比较。
2. 统一搜索—全文抓取—引用结构，并补通用 Agent 的全文工具。
3. 增加跨源证据矩阵、候选裁决和决策闭合质量门。
4. 持久化 N8N tool trace。
5. 增加运营/财务/分期场景校验。

### 最低验收标准

- 任一章节的每个空间数字都能追溯到 `scope_id`、快照、数据年份和空间关系。
- 同一项目至少能运行两个等时圈时间阈值，并输出范围差异及其对结论的影响。
- 每个候选定位或产品都能看到至少一个比较基准、一个反例或缺口，以及明确的采用/保留/退出状态。
- AnySearch 只有在全文抓取成功、来源主体和日期可识别时才计入可引用互联网证据。
- 财务或运营输入不足时报告显示 `not_calculable`，而不是生成伪精确数字。
- 从数据库中的 `tool_trace` 可以重建本次工具调用顺序、参数摘要、错误和证据集合。
- 删除或合并入口前完成调用统计、兼容期和相关测试迁移，避免误删前端仍在使用的内部接口。

## 8. 对论文和 proposal 的影响

论文中可以把当前 N8N 作为工程参考实现和实验对象，重点检验：统一等时圈边界、多源证据检索、结构化质量门和多智能体编排是否改善报告的证据完整性、空间一致性、决策闭合度和专家评分。

不能把“使用了 POI、人口、夜光和多智能体”直接写成方法有效；也不能把一次成功运行、引用数量或报告篇幅当作区域分析质量。若 P0 工具尚未完成，论文应把财务、运营、真实客流和因果判断明确列为系统不能证明的边界。
