# 空间分析报告 Agent V4 目标架构

## 1. 文档目的

本文定义空间分析报告 Agent V4 想要建设的产品，而不是当前代码的实现说明或迁移方案。

V4 的目标是形成一个能够理解空间项目、使用已有材料与空间数据、按需调用分析工具，并由多个专业角色共同产出完整项目报告的分析团队。它服务于城市更新、社区营造、商业选址、公共设施、文旅与空间运营等项目。

系统最终交付的应是一份帮助项目负责人作出下一步决策的专业报告，而不是指标清单、工具调用记录或证据审计台账。

## 2. 核心判断

证据、来源、指标口径、图表安全和工具调用记录仍然重要，但它们是系统可靠性的内部能力，不应成为报告 Agent 的主要工作对象。

报告生产的主流程应围绕专业判断展开：

```text
理解项目
→ 设计分析计划与报告结构
→ 按章节研究、分析和写作
→ 编辑审校与一次针对性退修
→ 交付完整报告
```

这意味着主分析师和专业 Subagent 关注的是项目问题、替代方向、数据能够支持的判断、数据不能支持的边界，以及对项目的行动建议。它们不需要管理工具重试、哈希、适配器、指标执行计划或证据对象的访问锁。

## 3. 产品目标

V4 必须做到：

- 从项目材料、历史版本、地图范围、空间对象、已有数据和既有分析结果形成项目理解。
- 根据项目的真实决策问题动态生成报告大纲，而不是套用固定章节模板。
- 由具备完整判断责任的专业角色直接写出可发布章节，而不是由数据类型 Agent 提交零散 Memo。
- 允许研究过程中根据新发现补充指标、调整问题和修正章节重点。
- 让每一项关键判断明确区分事实、代理数据、推断和建议，并说明重大不确定性。
- 通过主分析师审校解决遗漏、矛盾、越界结论和不可执行建议。
- 直接组装通过审校的章节，避免再次概括为缩水的二次报告。

V4 不追求把开放式分析改造成监管级审计系统，也不追求以更多中间 JSON 对象代替专业思考。

## 4. 用户与适用场景

主要用户是需要理解空间项目并推动决策的策划、更新、投资、运营、设计和公共事务团队。典型问题包括：

- 项目应优先服务谁，解决什么问题？
- 空间区位、可达性、周边设施和竞争关系允许或限制什么？
- 哪些需求、文化资产或功能组合值得投入，哪些仍只是待验证假设？
- 多种发展方向中，哪一种更适合当前条件？
- 首期应做什么试验，满足哪些条件后才能扩张，什么情况下应停止？

不同项目可以使用不同报告结构。社区更新、商业选址、公共设施和文旅项目不应被迫启用相同章节或相同专业角色。

## 5. 工作流

```mermaid
flowchart LR
    A[项目文档、地图范围和已有数据] --> B[主分析师理解项目]
    B --> C[动态分析计划与章节设计]
    C --> D[建立章节 DAG 与专业任务]
    D --> E[基础章节并行研究]
    E --> F[依赖章节按条件启动]
    F --> G[主分析师总编辑审校]
    G -->|上游变更时定向复核下游| F
    G --> H[编译通过审校的章节]
    H --> I[项目报告与图表]
```

### 5.1 项目理解

主分析师阅读原始材料和已有分析结果，形成项目背景、关键事实、主要矛盾、待决策问题、已知边界和初步报告逻辑。这里的目标是理解项目，而不是先穷举所有指标或冻结证据需求。

### 5.2 分析计划与章节设计

主分析师形成动态分析计划。每个章节任务应说明：

- 本章存在的原因和必须回答的问题；
- 所需阅读的项目材料和可参考的既有章节；
- 可使用的已有数据、图表与候选指标工具；
- 应交付的小节、比较、图表或行动建议；
- 与其他章节的边界和依赖关系。

计划是研究的方向，不是不可变的前置锁。新发现可促使主分析师调整后续章节任务；已完成章节若受影响，则由编辑阶段明确退修。

### 5.2.1 动态章节 DAG

章节不应平铺启动。分析计划将章节组织为无环依赖图：没有上游依赖的基础章节可并行研究；依赖空间、需求、资产或策略判断的章节，在所需输出可用后启动。

每条依赖边标明所需输出，而不只是引用上游章节 ID：

- `context`：需要背景、材料或数据目录；上游初稿可用后即可启动。
- `finding`：需要上游的专业判断；上游形成可引用版本后启动。
- `decision`：需要上游的推荐结论；上游审校通过后启动。

上游结果不可用时，下游应将其作为明确边界继续完成可独立成立的分析；只有该结果对下游核心结论不可替代时，才阻塞该章节。上游章节退修后，只复核和退修依赖该变更输出的下游章节，不全量重跑报告。

### 5.3 专业研究与章节写作

专业 Subagent 在一个连续任务中完成阅读、按需工具调用、比较、解释、图表选择和正式章节写作。每个章节应具有完整的专业论证：

```text
判断
→ 依据或数据边界
→ 比较基准
→ 可能机制
→ 对项目的影响
→ 行动建议
→ 条件、不确定性与验证方式
```

这是一项写作与审查质量要求，不要求把每段正文拆成固定字段。没有数据支持的内容可以作为假设、待验证方向或明确的数据缺口出现，但不能伪装为既成事实。

### 5.4 编辑审校与交付

主分析师作为项目负责人和总编辑，检查章节是否回答任务、专业判断是否完整、事实与推断是否混淆、数字是否可追溯、章节间是否冲突、图表是否帮助理解，以及建议能否从分析中推出。

不合格章节退回原作者进行一次针对性修订。主分析师可撰写执行摘要、跨章节综合结论、章节过渡和最终建议，但不得静默替换专业作者的关键判断。

## 6. 角色模型

### 6.1 固定角色：主分析师 / 总编辑

主分析师是唯一固定角色，负责：

- 完整理解项目并识别真正的决策问题；
- 动态设计报告结构和章节责任；
- 从专业角色池中选择适当的章节分析师；
- 管理章节依赖、跨章信息传递和冲突处理；
- 审校章节、发起一次退修，并完成综合结论；
- 确保报告的建议、边界和下一步验证任务清晰一致。

主分析师不是全文代笔者，也不是指标执行管理员。

### 6.2 动态专业角色池

专业角色按完整的判断责任划分，不按 POI、H3、人口、夜光或文档等数据类型划分。主分析师通常从角色池中选择 3 至 6 个角色，并可根据项目重新命名或组合。

| 角色模板 | 负责回答的问题 | 常用材料与工具 |
| --- | --- | --- |
| 空间与区位分析师 | 空间环境允许什么、不适合什么？ | 区位、路网、等时圈、POI、人口、夜光、H3、地图 |
| 市场与需求分析师 | 谁会使用、为什么来、使用频率如何？ | 人口、设施供给、竞品、访谈、观察、消费与客流资料 |
| 项目资产与内容分析师 | 项目有哪些可转化资产，能否形成持续内容？ | 历史档案、建筑与空间资料、社区记录、运营资料 |
| 定位与经营策略分析师 | 应选择什么发展组合和功能结构？ | 已完成章节、竞品、投资与运营资料、方案比较 |
| 实施与风险分析师 | 如何分阶段验证、推进、调整或停止？ | 项目条件、审批、资金、运营责任、试验和绩效资料 |

角色名称不是固定 schema。例如，公共设施项目可启用“服务覆盖与空间公平分析师”，商业选址项目可启用“竞争与业态分析师”，文旅项目可启用“旅游流线分析师”和“文化产品分析师”。

### 6.3 章节边界

章节以判断责任划分。空间章节对“空间条件允许和限制什么”负责；需求章节对“谁真正需要和使用项目”负责；策略章节对“应选择什么方向”负责。一个角色可以使用多类数据，但不能把其他章节的核心判断悄然替代。

数据与图表服务不单独写“数据章节”。它们响应专业 Agent 的问题，返回结果、口径、限制和可用图表；业务解释和项目判断始终由章节作者负责。

## 7. 信息与工具边界

### 7.1 公开的报告工件

报告运行只保留少量对专业协作有意义的公开工件：

```text
run/
├── source-index.json
├── analysis-plan.json
├── chapters/
│   ├── <chapter-id>.v1.json
│   └── <chapter-id>.v2.json       # 仅在退修时出现
├── editorial-review.json
└── report/
    ├── project-report.md
    └── assets/*.svg
```

- `source-index` 是材料、数据、历史结果、轻量分析结果和图表资源目录，包含可用状态、时间与空间范围；它不是证据审计模型。
- `analysis-plan` 保存项目理解、核心问题、动态大纲、章节任务、依赖、建议材料和候选工具。
- `chapter` 保存可直接进入报告的完整正文、轻量引用、使用的指标与图表、数据缺口和作者不确定性。
- `editorial-review` 保存章节决定、问题、冲突、退修要求、最终采用版本，以及编辑撰写的摘要和综合建议。

### 7.2 轻量分析结果层

每次工具生成且可复用的指标结果，均作为 `source-index` 中的一条轻量分析结果记录，分配稳定结果 ID。章节作者、图表和最终报告可引用同一个结果 ID，而不重复计算或重新描述其口径。

分析结果记录只包含复用所需的信息：

- 结果 ID、工具或指标名称及版本；
- 空间范围、时间范围和必要参数；
- 结果摘要、结构化结果和输入来源；
- 适用限制与成功、不可用或失败状态；
- 可复用图表或资产引用。

结果层不保存全局证据需求、章节访问白名单、claim registry 或工具编排细节。参数执行、适配器、重试和底层日志继续由工具模块内部管理。

### 7.3 轻量引用

报告正文可以用稳定资源 ID 引用项目文件、数据集、指标结果和图表。每个章节在末尾列出实际使用的材料、指标、图表和关键缺口。

引用的目的，是让读者和编辑确认“这个判断基于什么”，而不是要求作者管理复杂证据对象。系统应校验引用目标存在，数值应能追溯至已记录的指标结果；不要求生成 claim registry。

### 7.4 下沉的可靠性机制

以下能力仍应存在，但由拥有执行上下文的模块内部处理：

- 工具参数、适配器、缓存、重试、失败原因和调用日志；
- 指标口径、输入校验、空间对象处理、坐标和几何修复；
- 数据读取状态、图表渲染来源和 SVG 安全检查；
- 文件哈希、发布原子性和运行诊断。

主分析师和专业章节作者只需要获得能够指导分析的结果、限制和可用资源，不需要操作这些内部机制。

### 7.5 空间制图、报告视觉与 ArcGIS 执行边界

报告视觉是帮助读者理解已归档材料、数据和专业判断的表达层，不是独立作出业务结论的分析主体。V4 保持以下公开资产契约不变：可复用分析结果写入 `source-index.json`，视觉资产写入 `report/assets/*.svg`，章节和最终报告只通过稳定的 `result ID`、`asset ID` 和材料资源 ID 引用它们。

`asset ID` 是报告视觉的唯一公开引用。一个视觉资产只能依赖已经登记的材料、数据集、历史结果或分析结果；专题图和图表可以帮助解释这些资源，但不得在未形成可复用结果的情况下制造新的数值、判断或推荐。

未来的正式报告视觉链路分为两类：

- **空间地图**：专题图、透明空间叠加图、空间统计图和网络上下文图；它们由受限的 ArcGIS 空间能力生成，并且必须保留所依赖结果、范围和限制。
- **非地图图表**：柱线图、散点图、时间线、关系图和其他报告表达图；它们同样由受限 ArcGIS 服务的 ArcGIS Pro Layout / 图表布局模板生成，只表达已归档的数据视图和结论边界。

主分析师和章节作者只决定是否需要图、图要帮助回答什么问题、应引用哪些已有资源。图层准备、数据视图、空间参考、样式、布局、导出、缓存、失败诊断和 SVG 安全检查由拥有执行上下文的深模块处理。章节作者不接触 ArcGIS/MCP 工具名、图层字段、服务地址、ArcPy 参数、token、renderer JSON 或执行日志。

本地 `render_report_visual`、`simple_map` 及其测试已从 V4 链路移除。所有六类报告视觉通过受限 ArcGIS 报告视觉模块生成；若受限服务不可用，系统返回带有原因的 `unavailable` 或 `failed`，不伪造图表或替代数值。

所有输出 SVG 在进入 `report/assets/` 前必须经过统一安全校验。空间地图、叠加结果、空间统计和网络覆盖只能描述可观察的空间条件、关联、覆盖或显著性；它们不能单独外推为消费、真实客流、营收、投资回报或确定性选址结论。网络能力服务于研究范围、道路走廊、区域覆盖和区域比较。

## 8. 分析与表达质量

V4 要求所有专业角色遵守以下共同原则：

1. 阅读原始项目材料，而不只依赖主分析师摘要。
2. 工具服务于问题；没有明确分析价值时，不为了调用而调用。
3. 区分直接事实、代理数据、推断和建议。
4. 使用同层级的替代方向或比较基准，不只罗列现状。
5. 将空间或数据现象解释为项目影响和可执行行动。
6. 明确可能推翻建议的条件、关键数据缺口和验证办法。
7. 主动使用人口、夜光、POI 和路网数据识别空间条件与行为线索：人口可用于判断服务覆盖、潜在使用人群和需求分层；夜光可用于识别夜间活动强度与时空差异；POI 可用于分析供给结构、功能混合、竞品与服务缺口；道路连通性可用于判断可达性、路径摩擦和潜在流线。作出购买力、真实消费、实际客流或确定需求等结论时，必须结合收入或消费、客流观察、交易、访谈、运营数据或明确的验证任务，并说明代理指标的适用边界。
8. 将项目愿景视为需要检验和落地的项目假设与设计约束：它可以决定分析应比较哪些方向、空间应解决哪些问题，但不能单独证明市场需求、运营主体、收入机制或财务可行性已经成立。报告应说明哪些外部证据支持或挑战该愿景，以及仍需完成哪些验证。

报告中的不确定性不应使分析停止。只有当缺失信息可能逆转推荐方向、改变关键空间安排或使方案不可实施时，才将其升级为必须完成的验证任务。

## 9. 范围与非目标

V4 的范围是项目级空间分析与专业报告协作。它不承担以下目标：

- 监管、法律或尽调场景所需的逐条可审计结论登记；
- 以固定专业数量或固定章节模板覆盖所有项目；
- 让数据工具或图表模块代替专业作者进行业务判断；
- 在缺少市场、运营、技术或财务资料时伪造精确可行性结论；
- 用复杂中间对象限制开放式研究的方向调整。

如果未来出现法律、融资尽调或监管级交付需求，应在 V4 之上单独增加审计模式，而不是把审计契约重新放回日常报告主流程。

## 10. 成功标准

V4 成功时，项目团队能够清楚看见：

- 这个项目真正要决定什么；
- 每个章节由谁负责、为什么存在、回答了什么；
- 哪些结论来自材料或数据，哪些仍是有条件的推断；
- 不同专业判断如何汇聚为推荐方向；
- 下一步应补什么信息、做什么低成本试验，以及什么条件下继续、调整或停止。

从系统角度看，成功不是生成更多审计对象，而是更稳定地产出有深度、可解释、可讨论、可行动的空间项目报告。
