# 决策报告质量门槛

质量审校首先判断分析有没有穿透项目问题。事实正确、没有代理越界、章节齐全和视觉有效只是最低底线，不能据此判定报告合格。

## 分析深度一票退修

出现任一情况即退修：

1. 用户确认问题地图前已经启动专项研究、锁定定位、形成 `decision_inventory` 或生成正式大纲；
2. 正式大纲只是把人口、POI、夜光、路网或专家角色转换成章节名称；
3. 重要结论只引用材料或指标，没有解释证据通过什么机制支持该结论；
4. 推荐方向没有说明为什么优于真实候选方向，优势不能回到项目特有资产、关系、约束或使用机制；
5. 没有主动检验反例、失效条件和触发改判的信号，只写推荐成立的一面；
6. 空间或产品方案只列优点与功能，没有说明各自牺牲什么、制造什么后续约束；
7. 方案假定组织、内容生产、招商、服务交付或现场运营能力天然存在，没有识别能力缺口及其对实施顺序的影响；
8. 没有解释选择造成的路径依赖，以及改向、缩减、暂停或退出的成本和办法；
9. 报告没有揭示新的机制、矛盾或行动优先级，只是正确复述项目材料和空间指标；
10. 用“存在候选比较”“包含停止条件”等形式完整性代替具体推理；
11. 替换项目名称后，大部分分析仍可原样用于其他项目；
12. 任何影响决策的实质章节没有经过反方审查，或反方审查只复述质量检查清单；
13. 没有回应当前证据范围内能够成立的最强反驳，正文仍只呈现支持推荐的一面；
14. 分析深度审校员静默忽略反方意见，或没有裁定其是否推翻、降级或改变判断；
15. 重大深度问题只通过补一句边界或增加一个字段修补，没有退回相关分析环节重做。

## 反方审查

反方审查员先于分析深度审校员工作。它逐个影响决策的实质章节识别关键判断，并提出最强反方论证、替代解释、隐藏假设、遗漏冲突、方案代价、能力障碍和执行失败场景。批评必须指出具体章节哪里不好、为什么影响决策以及必须回应什么，不能泛称证据不足，也不能为完成形式制造无关意见。

反方审查使用自然 Markdown：

~~~text
章节与关键判断
→ 最强反方观点
→ 暴露的问题
→ 对决策的影响
→ 必须回应的问题
~~~

没有实质问题的章节明确记录“无重大反方意见”。分析深度审校员随后逐项裁定为接受、部分接受或不成立，并说明对当前判断的影响。成立的重大意见必须退回拥有相关决策的原章节 Subagent 定向返写；修订后重新审查受影响章节并复核整份报告。审校员与主 Agent 都不得直接代写专业正文。

原始反方意见和裁定只用于内部审校，不进入正文或证据审计。正文必须吸收成立的反例、代价、失败条件和改判逻辑，但不得展示角色名称、审查过程或内部备忘。

## 深度审校方法

先对照已确认的 `problem_map` 检查研究是否回应原始问题和反证，再用后置 `decision_inventory` 定位足以改变定位、空间、产品、运营或实施路径的重要判断。两者都不是待填表格，不增加供报告机械填写的深度字段。章节、段落和表格中出现了某个词，也不代表问题已经回答。

逐项检查：

- **机制**：证据与判断之间是否有可解释的因果或约束关系，而非相关性并列；
- **相对优势**：是否用同一项目问题比较真实候选方向，并解释推荐为何在当前条件下更优；
- **反证与失效**：是否提出足以推翻当前判断的反例、条件或观察信号，并说明届时如何改判；
- **方案后果**：空间、产品和运营选择是否揭示机会成本、冲突、依赖和后续限制；
- **承接能力**：所需组织与运营能力是否具体，缺口是否改变首开范围、合作方式或实施顺序；
- **可逆性**：是否说明如何低成本试验，以及扩大、改向、缩减、暂停和退出分别意味着什么；
- **分析增量**：报告是否把原始材料转成项目此前不明显但可用于行动的机制、矛盾或优先级。

闭环只有在解释了上述与当前判断相关的问题后才算成立。不是每个简单决策都要机械覆盖全部问题，但任何会改变行动的缺口都必须补足。复杂项目若对象关系、利益冲突、候选路径或实施阶段使分析未闭合，必须展开对应分析；简单项目可以合并表达。缺少直接客流、收入或投资数据不能成为不作判断的理由，也不能用伪造阈值制造深度。

分析深度审校发现重大问题或接受反方意见时，按以下结构返回，不给最小措辞修正：

~~~text
受影响的关键判断
→ 缺失的分析
→ 为什么会影响当前决策
→ 需要重新分析的上游问题
~~~

主 Agent 将问题路由回对应的区域、定位、空间或运营章节所有者。原作者沿用原证据包生成新版本，不覆盖旧稿。重大深度问题未解决前，不得进入视觉编辑和最终交付。

## 正式章节与装配一票否决

以下门槛只适用于 `formal_comprehensive` 正式综合报告；简单问答、单项诊断和局部分析不创建这些产物，也不触发章节长度检查。

出现任一情况即阻止正式报告交付：

1. 缺少 `report/chapter-index.json`、独立章节版本、对应审校文件或 `report/project-report.md`；
2. 同一重要决策由多个章节拥有，或章节没有明确专业所有者；
3. 下游章节依赖尚未接受或在索引顺序中位于其后的上游章节；
4. 版本不是从 v1 连续递增、旧版本被覆盖，或初稿后超过两次返写；
5. 接受版本不是最新版本，章节或最新审校仍有 `revision_required` 等未解决状态；
6. 全稿冲突审校发现重大意见后，主 Agent 静默合并或直接改写，而不是退回原章节所有者；
7. `project-report.md` 遗漏接受章节、使用错误版本、改变标记内正文、调整论证或压缩实质内容；
8. 执行摘要、过渡或综合结论代替专业章节，造成重要决策闭环只存在于主编摘要中；
9. PDF 样式按每个章节标题强制分页，导致正文被人为切成单页摘要式版面。

每个专业章节通常为 1,500-3,000 个中文内容字符。低于或超过长度带只产生审校警告，不自动通过或否决；事实正确但缺少机制、比较、代价、反例、能力缺口和退出路径的长章节仍必须返写，内容充分的短章节也可由深度审校明确接受。

装配前必须运行：

~~~text
python skills/spatial-business-analyst/scripts/validate_chapter_assembly.py --report-dir <report-directory>
~~~

命令失败时不得进入视觉渲染、HTML 或 PDF 导出。

## 正确性最低底线

以下任一情况同样一票否决，但全部通过仍不代表报告有深度：

- 项目事实、数值、来源、年份、范围或对象名称错误；
- 人口被当作确认客群，POI 被当作需求，夜光被当作夜间消费，路网指标被当作实测客流；
- 没有直接数据却预测销量、稳定订单、营收、投资回报或法定合规结论；
- 虚构项目对象，或遗漏会改变实施的真实对象关系；
- 定位、使用者、空间、产品和运营相互冲突；
- 多个段落只写“建议进一步研究、调研、核实”而没有当前动作；
- 通用免责声明、重复边界或待补资料占据摘要或正文主体；
- 地图或图表不会改变任何判断，或空白、失真、不可读却被称为真实数据视觉。

## 证据纪律

- 项目事实来自已读取原件或可用项目数据；
- POI 邻近、人口、夜光和路网明细来自 MCP 数据侧空间查询或实际指标结果；
- 同一比较明确范围、年份、空间单元和参数；
- 人口不是确认客群，POI 不是需求，夜光不是夜间消费，路网指标不是实测客流；
- 没有直接数据时不写销量、稳定订单、营收、投资回报或法定合规结论；
- 数据失败只降低相关判断，不用其他代理伪装直接证据。

## 表达密度

- 执行摘要先写定位和判断，不写方法流程；
- 一个段落只承担一个判断；
- 每个数字后必须有规划含义；
- 同一限制只出现一次；
- 不展示 Agent、Prompt、内部结构或工具日志；
- 附录承载证据台账和口径修正，正文承载决策。

## 对象与空间

根据 `project_semantic_model` 检查所有会影响定位、使用、运营或实施的真实对象及关系。对象必须保留原名，并标记为已计划、条件性、暂不纳入或阻断；不存在的建筑、开放空间、居民或活动机制不得由模板补出。多层级项目应在适合自身的系统、组团、单元或线性关系中说明承载逻辑，单体项目不强行套用多建筑结构。

资料不足时给出条件性或当前可逆建议，不得让对象盘点取代整体策略。

## 实施与运营

每个阶段必须有：

- 主要任务；
- 可交付成果；
- 进入下一阶段的条件；
- 对应的调整或停止动作。

这些要素必须解释实施逻辑，不能作为五列表格机械交差。首轮运营记录覆盖项目实际存在的到达、使用、服务完成、重复参与、冲突、成本或单位经济机制；不存在的机制不强制生成指标。未建立基线时先记录真实数据，不编造阈值。

## 视觉最低底线

视觉只作次级底线验收，不能替代分析深度，并完整遵守 `report-visual-workflow.md`：

- 正式综合报告必须由独立视觉 Subagent 完成评估；零图也要保存计划、manifest 和省略原因；
- 每项视觉必须来自真实持久化结果、当前批准模板并回指相邻判断；
- 正式报告中的视觉、锚点和题注只能位于章节标记之外，生成后装配验证仍须通过；
- 实际资产必须安全、可追溯、可读，并在 Markdown、HTML、PDF 和真实视口中无乱码、裁切、遮挡或溢出；
- 空白、失真、暗示代理数据能够证明经营结果，或删除后不改变相邻判断的视觉必须省略。

视觉失败时保留已有分析并记录省略，不用占位图阻塞报告。

## 最终删除测试

对每项数据和视觉提问：删除后，定位、空间、产品或运营决定是否变化？

- 不变化：从正文删除或移入附录；
- 变化：保留，并明确它改变了什么。

再对每项主要结论提问：如果删除项目名称和专有对象，推理是否仍可原样套用到其他项目？若可以，说明分析尚未触及项目特有机制，必须退修。
